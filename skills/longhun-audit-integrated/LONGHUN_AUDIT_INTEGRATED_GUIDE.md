## 融合的关键点

### 脚本能否执行的三层判定

```
┌─ 第一层：CNSH对齐
│  ├─ 包含简体"龍"？ → 🔴 FUSE_3熔断，不执行
│  └─ 违反底座原则？ → 🔴 语义错误，不执行
│
├─ 第二层：系统健康（执行前检查）
│  ├─ 依赖齐全？ → 否则提示装什么
│  ├─ 磁盘够用？ → 否则提示清理
│  └─ 权限正确？ → 否则提示chmod
│
└─ 第三层：执行中持续监控
   ├─ 行为是否异常？ → 日志记录
   └─ 性能是否正常？ → 性能报警
```

**最终决策：**

```
if 脚本_CNSH检查 == 🔴:
    拒绝执行("底座违反")
elif 系统_所有维度 >= 0.60:
    执行脚本()
else:
    执行前警告("系统存在问题")
```

## 与任务拆分的整合

**旧的检查流程（分散）：**
```
脚本 → CNSH对齐检查 ✓
脚本 → 系统健康检查 ✓
脚本 → 安全检查 ✓
...（各自独立）
```

**新的检查流程（融合）：**
```
脚本 → 完整审计系统
     ├─ CNSH对齐（脚本层）
     ├─ 文件/健康/安全/...（系统层）
     └─ 统一置信度评分 → 🟢/🡡/🔴

下一个脚本依赖检查 ✓ 上一个的综合评分，而不是各自独立
```

**优势：**
1. 单一事实来源（一个审计系统）
2. 置信度全局一致
3. DNA追溯完整（所有维度都有记录）
4. 自动化决策清晰（if...else完全确定）

## 常见问题

**Q: 为什么CNSH对齐和系统审计要分开计算？**

A: 脚本可能代码完美（🟢），但系统不健康（🔴）。需要分别了解，这样可以精确定位问题。

---

**Q: 如果系统某个维度🔴怎么办？**

A: 按维度对号入座修复：
- 文件审计🔴 → 增加DNA标记
- 健康审计🔴 → 检查磁盘/内存/目录
- 安全审计🔴 → 修正权限或清除污染
- 等等

---

**Q: 可以自定义权重吗？比如我觉得安全审计比其他的更重要？**

A: 当前版本所有维度权重相等（1/10）。如果需要自定义，可以修改 `audit_all()` 中的权重计算。

建议：在底座原则框架内，保持平衡。
