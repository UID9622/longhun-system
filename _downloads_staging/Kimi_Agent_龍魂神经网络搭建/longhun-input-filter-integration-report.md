## 1. 执行摘要

### 1.1 协议定位

"输入过滤与预处理协议v2.0"（以下简称IFP）是龙魂体系的**L0输入层基础设施**，位于所有现有技能的最前端，负责对所有进入体系的输入进行预处理和验证。

### 1.2 核心结论

| 评估项 | 结论 | 状态 |
|--------|------|------|
| **依赖关系** | IFP依赖L1基础层(governance/dna-align/system)，L3+应用层依赖IFP | ✅ 合理 |
| **冲突检测** | 发现4项潜在冲突，均可通过协调机制解决 | 🟡 需关注 |
| **排序位置** | 建议定位为L0（输入层），加载顺序第4位 | ✅ 推荐 |
| **接口设计** | 统一网关入口 + MCP工具暴露 | ✅ 可行 |

### 1.3 关键发现

- **无破坏性冲突**：IFP与现有52个技能体系无根本性冲突
- **依赖方向正确**：IFP作为输入层，下游技能（L3-L4）应依赖它
- **协调机制可行**：所有检测到的重叠可通过接口协调解决
- **MCP集成路径清晰**：可通过longhun-cloud-mcp暴露为标准工具

## 3. 冲突检测结果

### 3.1 冲突总览

| # | 冲突类型 | 涉及技能 | 严重度 | 状态 |
|---|----------|----------|--------|------|
| C1 | 优先级机制冲突 | longhun-governance(三层监督) | 🟡 中 | 可协调 |
| C2 | 熔断机制冲突 | longhun-cloud-kimi(断路器) | 🟡 中 | 可协调 |
| C3 | 语义提取重叠 | longhun-empower-engine(关键字路由) | 🟡 中 | 可协调 |
| C4 | 自检清单冲突 | longhun-formula-opt(权重缓存) | 🟢 低 | 可协调 |

### 3.2 冲突C1：IFP 4步优先级 vs Governance三层监督

**冲突描述：**

| 系统 | 优先级机制 | 处理阶段 |
|------|-----------|----------|
| IFP v2.0 | 4步优先级（语义提取→冲突检测→缺失识别→确认） | 输入预处理阶段 |
| Governance v5.0 | 三层监督（感知层→认知层→决策层） | 全生命周期 |

**冲突分析：**

```
IFP 4步优先级:
  Step1: 语义锚点提取（关键词扫描→结构化封装→清洗）
  Step2: 多维冲突检测（数值一致性→边界越界→冲突熔断）
  Step3: 缺失项识别（完备性自检→假设前置声明）
  Step4: 交互确认（主动核实→DNA证据链）

Governance 三层监督:
  Layer1: 感知层筛查（格式/完整性/注入检测）
  Layer2: 认知层验证（逻辑/语义/偏见检测）
  Layer3: 决策层审核（通过/警告/阻断）
```

**判定结果：🟡 中 — 职责重叠但层级不同**

**详细分析：**
- IFP Step1（语义提取）与Governance感知层筛查有功能重叠：两者都检查输入格式和完整性
- IFP Step2（冲突检测）与Governance认知层验证部分重叠：都进行一致性检查
- **关键差异**：IFP专注于**输入预处理**（前置），Governance专注于**全生命周期治理**（贯穿）

**协调方案：**
```python
# 推荐：IFP感知层 → IFP预处理 → Governance全链路监督

协调接口:
  IFP.语义提取() 的输出 → 作为 Governance.感知层筛查() 的输入
  IFP.冲突检测() 的发现 → 作为 Governance.认知层验证() 的参考

明确职责边界:
  · IFP：负责输入"质量"预处理（清洗/结构化/补全）
  · Governance：负责行为"合规"治理（逻辑/价值观/安全性）
```

### 3.3 冲突C2：IFP冲突熔断 vs Kimi断路器

**冲突描述：**

| 系统 | 熔断机制 | 触发条件 | 恢复策略 |
|------|----------|----------|----------|
| IFP v2.0 | 冲突熔断（多维） | 数值不一致/边界越界 | 立即阻断+人工审核 |
| Kimi v5.0 | 断路器模式 | 3次API故障 | 30秒超时恢复 |

**冲突分析：**

```
IFP 冲突熔断:
  触发：输入数据存在数值不一致、边界越界
  行为：立即阻断请求，不向下游传递
  范围：输入验证层
  恢复：人工审核后手动放行

Kimi 断路器:
  触发：连续3次API调用失败
  行为：断开API连接，转本地备份推理
  范围：服务调用层
  恢复：30秒后自动试探恢复
```

**判定结果：🟡 中 — 层级不同但概念相似，需避免命名混淆**

**详细分析：**
- 两者都使用"熔断"概念，但作用于完全不同的层级
- IFP的熔断是**数据质量**熔断（输入维度）
- Kimi的断路器是**服务可用性**熔断（服务维度）
- 可能产生命名和日志记录的混淆

**协调方案：**
```python
# 推荐：命名空间隔离

IFP熔断命名:
  · 数据熔断 (data-break) — IFP专有
  · 数值越界熔断 (value-overflow-break)
  · 冲突熔断 (conflict-break)

Kimi断路器命名:
  · 服务断路器 (circuit-breaker) — Kimi专有（保持原有）
  · 故障断路器 (fault-breaker)

# 统一日志前缀
IFP日志: "[IFP-DATA-BREAK] 🔴 数值越界熔断触发"
Kimi日志: "[KIMI-CIRCUIT] 🔴 断路器断开状态"
```

### 3.4 冲突C3：IFP语义提取 vs Empower-Engine关键字路由

**冲突描述：**

| 系统 | 关键词处理 | 输出用途 | 处理阶段 |
|------|-----------|----------|----------|
| IFP v2.0 | 语义锚点提取（结构化封装/清洗） | 输入标准化 | 预处理 |
| Empower-Engine v1.5 | 10大类关键字识别+9人格路由 | 需求路由 | 业务处理 |

**冲突分析：**

```
IFP 语义提取:
  功能：提取关键词 → 结构化封装 → 清洗非结构化数据
  输出：标准化的结构化输入数据
  目的：确保输入可被下游正确处理

Empower-Engine:
  功能：10类关键字匹配(M01-M10) → 9人格路由(P01-P15)
  输出：路由决策（调用人格+优先级）
  目的：将用户需求路由到最合适的处理人格
```

**判定结果：🟡 中 — 处理阶段不同但关键词识别逻辑可能重复**

**详细分析：**
- IFP的"语义锚点提取"与Empower-Engine的"关键字识别"在底层都是关键词扫描
- 两者可能维护各自的关键词库，造成冗余和不一致
- IFP的清洗可能移除Empower-Engine需要的原始关键词

**协调方案：**
```python
# 推荐：IFP标准化输出 → Empower-Engine消费

协调接口:
  IFP.语义提取(原始输入) → 结构化数据 {
      "清洗后文本": str,          # Empower-Engine处理用
      "原始关键词列表": list,      # Empower-Engine关键字匹配用
      "结构化字段": dict,          # 下游直接消费
      "数据质量评分": float,       # Governance审计用
      "假设前置声明": list         # 缺失项声明
  }

  Empower-Engine.识别需求(IFP输出) → 路由决策

# 关键词库共享
建立统一关键词词库:
  · IFP负责：技术关键词（用于输入验证）
  · Empower-Engine负责：业务关键词（用于需求分类）
  · 交集部分：通过共享配置同步
```

### 3.5 冲突C4：IFP Pre-flight Check vs Formula-Opt权重缓存

**冲突描述：**

| 系统 | 检查机制 | 检查内容 | 触发时机 |
|------|----------|----------|----------|
| IFP v2.0 | Pre-flight自检清单（5项） | 输入完备性/假设声明 | 每次请求 |
| Formula-Opt v5.2 | 权重缓存系统 | 小规模开销分析/缓存命中 | 权重计算时 |

**冲突分析：**

```
IFP Pre-flight Check (5项):
  1. 输入非空检查
  2. 格式合规检查
  3. 必需字段完整性检查
  4. 假设前置声明检查
  5. DNA追溯标记检查

Formula-Opt 权重缓存:
  · 小规模开销分析（数据量<10跳过缓存）
  · 权重缓存命中/未命中统计
  · 缓存预热策略
```

**判定结果：🟢 低 — 几乎无直接冲突，仅检查时机可能重叠**

**详细分析：**
- IFP的Pre-flight是**输入验证**（请求级别）
- Formula-Opt的权重缓存是**计算优化**（算法级别）
- 两者在"小规模数据优化"理念上相似，但实现层面完全不同

**协调方案：**
```python
# 推荐：保持独立，IFP可选调用Formula-Opt

IFP.Pre-flight扩展（可选集成）:
  def Pre-flight自检清单(输入数据):
      基础5项检查()  # IFP原生

      # 可选：大规模数据时调用Formula-Opt分析
      if 数据量 > 阈值:
          缓存建议 = Formula-Opt.小规模开销分析(数据量)
          检查结果.缓存优化建议 = 缓存建议

      return 检查结果
```

```python
# 操作台API集成 — 通过中间件模式

# 文件: longhun-cloud-panel/scripts/操作台API.py

class 输入过滤中间件:
    """
    操作台输入过滤中间件
    拦截所有进入操作台的请求，进行IFP预处理
    """

    def __init__(self, 过滤器: 输入过滤协议):
        self.过滤器 = 过滤器
        self.审计器 = 三色审计器()  # from governance

    async def 处理请求(self, 请求: Request) -> Response:
        # Step 1: Pre-flight自检
        自检结果 = self.过滤器.Pre_flight自检(请求)
        if not 自检结果.通过:
            self.审计器.红记录("IFP", f"Pre-flight失败: {自检结果.原因}")
            return Response(400, {"错误": 自检结果.原因, "DNA": 生成DNA()})

        # Step 2: 语义提取
        语义结果 = self.过滤器.语义锚点提取(请求)

        # Step 3: 冲突检测
        冲突报告 = self.过滤器.多维冲突检测(语义结果.结构化数据)
        if 冲突报告.有冲突:
            self.审计器.黄记录("IFP", f"检测到冲突: {冲突报告.冲突列表}")
            if 冲突报告.需熔断:
                return Response(422, {"错误": "输入冲突", "详情": 冲突报告})

        # Step 4: 缺失识别
        缺失报告 = self.过滤器.缺失项识别(语义结果.结构化数据)

        # Step 5: 将处理后的请求传递给操作台路由
        处理后请求 = self._构建处理后请求(语义结果, 缺失报告)
        return await self.下游处理(处理后请求)

# 操作台注册中间件
操作台 = 操作台API()
IFP = 输入过滤协议()
操作台.添加中间件(输入过滤中间件(IFP))
```

```python
# 统一调用入口 — 支持多种集成模式

class 输入过滤网关:
    """
    IFP统一网关入口

    """

    # ═══════════════════════════════════════════
    # 模式1: 同步调用（适合轻量级预处理）
    # ═══════════════════════════════════════════
    def 同步过滤(self, 原始输入: Any, 必需字段: list = None) -> 过滤结果:
        DNA = self.DNA追溯器.创建子节点(父DNA, "INPUT-FILTER", "v2.0", "同步过滤")
        self.审计器.绿记录("IFP-GATEWAY", f"同步过滤请求: {DNA}")
        return self.过滤器.全流程处理(原始输入, 必需字段)

    # ═══════════════════════════════════════════
    # 模式2: 异步调用（适合复杂预处理）
    # ═══════════════════════════════════════════
    async def 异步过滤(self, 原始输入: Any, 必需字段: list = None) -> 过滤结果:

        return await self.过滤器.异步全流程处理(原始输入, 必需字段)

    # ═══════════════════════════════════════════
    # 模式3: 流式调用（适合实时数据流）
    # ═══════════════════════════════════════════
    async def 流式过滤(self, 数据流: AsyncIterator) -> AsyncIterator:

        self.审计器.绿记录("IFP-GATEWAY", f"流式过滤启动: {DNA}")
        async for 数据块 in 数据流:
            yield self.过滤器.快速预处理(数据块)

    # ═══════════════════════════════════════════
    # 模式4: 批量调用（适合大数据处理）
```

## 7. 风险与缓解措施

### 7.1 风险矩阵

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| IFP引入性能瓶颈 | 中 | 高 | 支持异步/流式/批量模式，缓存中间结果 |
| 与下游技能接口不兼容 | 低 | 高 | 提供适配器模式，保持向后兼容 |
| 关键词库维护不一致 | 中 | 中 | 建立共享配置中心，版本化管理 |
| DNA追溯链断裂 | 低 | 高 | 双重验证机制，fallback到governance |
| 审计日志膨胀 | 中 | 低 | 自动轮转，分级存储 |

### 7.2 关键成功因素

1. **零侵入集成**：IFP作为中间件，不修改现有52个技能的代码
2. **向后兼容**：所有现有API保持不变，IFP提供增强
3. **性能保证**：IFP处理延迟 < 5ms（标准模式）
4. **审计全覆盖**：所有IFP操作均记录三色审计日志
