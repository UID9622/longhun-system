## Abstract

We introduce Behavioral Cryptography, a multi-factor provenance framework for authenticating human-AI collaborative content. Instead of asking only whether content was generated by AI, the framework asks a richer provenance question:

Who originated this content, through which rules, personas, decisions, revisions, and audit traces did it pass, and what verifiable evidence remains?

Existing provenance approaches, including content credentials, synthetic content transparency standards, and statistical watermarking, primarily focus on media-level metadata, model-level disclosure, or token-level signals. These approaches are valuable but insufficient for complex human-AI co-creation, where authorship is distributed across human intention, AI-assisted formalization, rule-based workflows, revision history, and semantic continuity.

Behavioral Cryptography adds a semantic-behavioral lineage layer consisting of seven verification factors: Identity DNA, Temporal Anchor, Rule Trace, Persona Route, Protected Lexicon, Style Vector, and Mistake Ledger. Together, these factors form an evidence chain that may be easy to imitate at the surface-text level but difficult to forge as a complete lineage.

We instantiate this framework in the Longhun System, a civilian-grade human-AI collaboration system developed independently by UID9622. The framework is designed especially for independent contributors whose intellectual lineage may be erased or absorbed by institutional platforms.

1｜Introduction

1.1 The Provenance Gap in Human-AI Co-Creation

Generative AI has created a new authentication problem. Traditional detection systems typically ask:

Was this generated by a machine?

However, in human-AI collaboration, this question is too narrow. A more useful question is:

What human intention, decision process, rule system, and audit trail produced this content?

This distinction matters because modern content is rarely produced by a single isolated actor. A creator may use multiple AI systems, local tools, memory systems, translation layers, audit rules, and publishing workflows. In such contexts, surface text alone cannot capture provenance.

Current systems face several limitations:

- AI-detection methods are fragile against paraphrasing and multi-model laundering.
- Media provenance standards often depend on institutional adoption.
- Token-level watermarking may not survive editing, summarization, or translation.
- Independent creators often lack the infrastructure to prove intellectual lineage.
- Human-AI co-authorship is rarely represented as a structured evidence chain.

Behavioral Cryptography addresses this gap by treating provenance as a multi-factor verification problem.

2｜Related Work

Existing approaches to AI provenance and content authentication can be grouped into three broad categories.

2.1 Media Provenance and Content Credentials

Standards such as content credentials and media provenance frameworks focus on recording edit history, source metadata, and publication chains. These systems are important for images, video, and institutional media workflows.

However, they generally do not capture deeper behavioral lineage, such as:

- which rules guided generation;
- which human decisions changed direction;
- which protected terms must remain intact;
- which AI collaborators contributed formalization;
- which revision mistakes were recorded and corrected.

Behavioral Cryptography complements media provenance by adding a semantic-behavioral evidence layer.

2.2 Statistical Watermarking and AI Detection

Statistical watermarking and AI-detection methods attempt to identify machine-generated text or model-specific traces. These techniques can be useful in controlled environments but are vulnerable to paraphrasing, translation, summarization, multi-model rewriting, and manual editing.

Behavioral Cryptography does not depend on detecting whether content is AI-generated. Instead, it verifies whether a claimed lineage is consistent with a structured evidence chain.

2.3 Audit Trails and Workflow Provenance

Enterprise audit systems record workflow events, permissions, and logs. These systems are often designed for organizations with compliance budgets and centralized infrastructure.

Behavioral Cryptography aims to make provenance usable by independent civilian creators through lightweight, human-readable, locally controlled signatures and logs.

3.2 Seven-Factor Verification Mechanism

3.2.1 Formal Definitions

Definition 3.1 — Content Artifact

Let C denote a digital content artifact. C may be a text document, code file, image description, prompt, decision record, protocol page, or AI-assisted output.

Definition 3.2 — Behavioral Signature

The behavioral signature of C is defined as a seven-factor tuple:

Sigma(C)=langle F_1,F_2,F_3,F_4,F_5,F_6,F_7rangle

where each F_i is an independently verifiable provenance factor.

Definition 3.3 — Verification Oracle

A verification oracle is defined as:

V(Sigma(C),E)rightarrow(conf,evidence)

where:

- E is the claimed originator;
- conf in [0,1] is the composite confidence score;
- evidence is an append-only verification log;
- conf=0 means rejection;
- conf geq tau means acceptance under threshold tau.

Definition 3.4 — Hard Failure

A hard failure occurs when any critical factor returns:

score_i = 0

In this case:

conf = 0

This prevents one strong factor from compensating for a broken root.

3.2.3 Composite Verification Algorithm

def BehavioralSignatureVerify(C, E) -> tuple[float, "EvidenceLog"]:

```python
signature = parse_signature(C)
evidence = EvidenceLog()
factor_scores = []
verifiers = [
    verify_F1,
    verify_F2,
    verify_F3,
    verify_F4,
    verify_F5,
    verify_F6,
    verify_F7,
]
for i, verifier in enumerate(verifiers):
    factor_key = f"F{i+1}"
    score, log = verifier(signature[factor_key], E, C)
    factor_scores.append(score)
    evidence.add({
        "factor": factor_key,
        "score": score,
        "log": log,
    })
if any(score == 0.0 for score in factor_scores):
    evidence.add({
        "event": "HARD_FAILURE",
        "reason": "At least one verification factor returned 0.0",
    })
    return 0.0, evidence
weights = [0.25, 0.15, 0.15, 0.12, 0.12, 0.11, 0.10]
conf = weighted_geometric_mean(factor_scores, weights)
evidence.add({
    "event": "COMPOSITE_CONFIDENCE",
    "confidence": conf,
    "weights": weights,
})
return conf, evidence
```

辅助函数：

def weighted_geometric_mean(scores: list[float], weights: list[float]) -> float:

```python
product = 1.0
total_weight = sum(weights)
for score, weight in zip(scores, weights):
    product *= score ** weight
return product ** (1.0 / total_weight)
```

def digit_root(value: int) -> int:

```python
if value == 0:
    return 0
value = abs(value)
while value >= 10:
    value = sum(int(d) for d in str(value))
```

8｜Limitations

Behavioral Cryptography has limitations:

1. It does not replace legal authorship adjudication.
2. Style vectors are probabilistic and should not be treated as absolute identity proof.

5. Mistake ledgers must be designed carefully to avoid privacy harm or reputational misuse.
6. Protected lexicons can help preserve attribution but cannot alone prove authorship.
7. The system requires disciplined logging to maintain high evidence quality.

3.3 Threat Model and Adversarial Capabilities

3.3.1 Overview

We consider an adversary whose goal is to falsely claim authorship lineage over a content artifact legitimately generated by another originator. The adversary may copy, paraphrase, translate, summarize, reformat, stylize, or repackage the artifact through one or more AI systems.

We distinguish between two types of forgery:

1. Surface-level forgery: copying or modifying the visible content.
2. Lineage-level forgery: attempting to reproduce the behavioral evidence chain behind the content.

Behavioral Cryptography is designed primarily to resist lineage-level forgery. It does not claim that text, images, or code cannot be copied. Instead, it claims that copying the full behavioral lineage — including identity DNA, temporal anchors, rule traces, persona routes, protected lexicon continuity, style vectors, and mistake ledger history — is substantially harder than copying the surface artifact.

In simpler terms:

Copying content is easy.

Copying the verified path by which the content came into being is hard.

3.3.6 Trust Assumptions

The system requires several explicit trust assumptions.

T1. Key Security

The originator’s private signing key is not compromised.

If this assumption fails, F1 becomes unreliable.

T2. Ledger Integrity

Audit logs are append-only or periodically anchored to an external checkpoint.

If logs are freely mutable, F3 and F7 weaken.

T3. Registry Integrity

Persona registries, protected lexicons, and rule registries are versioned and signed.

If registries can be rewritten silently, F3, F4, and F5 weaken.

T4. Baseline Corpus Integrity

Style-vector baselines are computed from verified corpora.

If the baseline corpus is polluted, F6 weakens.

T5. Privacy-Constrained Logging

Mistake ledgers and behavioral logs must avoid exposing private content unnecessarily.

If logging becomes invasive, the system violates its own civilian-sovereignty goal.

3.3.9 Failure Modes

Behavioral Cryptography can fail or weaken under the following conditions.

FM1. Missing Logs

If the creator does not maintain rule traces, persona routes, or mistake ledgers, the system cannot reconstruct lineage.

Mitigation:

- automatic local audit logs
- lightweight JSONL ledger
- periodic hash snapshots

FM2. Over-Logging Privacy Risk

If every mistake or interaction is recorded in full, the system may expose sensitive information.

Mitigation:

- summary_only retention
- hash_only for sensitive entries
- burn mode for temporary processing
- sealed mode for highly sensitive content

FM3. Style Drift

A legitimate creator’s style may change over time.

Mitigation:

- use rolling baseline corpus
- avoid treating F6 as hard identity proof
- combine F6 with F1/F3/F7

FM4. Cultural Marker Misinterpretation

Shichen, wuxing, digit root, and other cultural-temporal markers may be misunderstood by reviewers unfamiliar with the system.

Mitigation:

- explain as human-readable temporal-semantic metadata
- avoid claiming mystical security
- position as cultural encoding plus consistency check

FM5. Key Compromise

If signing keys are compromised, identity verification weakens.

Mitigation:

- key rotation
- revocation record
- hardware-backed key storage
- public checkpointing
- multi-factor lineage verification

3.3.11 Design Implication

The threat model leads to one central design implication:

The system should not rely on any single proof.

3.4 The Dynamic DNA Engine

3.4.1 Motivation

The threat model in Section 3.3 shows that surface-level content can be copied, paraphrased, translated, and reformatted with minimal effort. A provenance framework therefore requires a lightweight mechanism that binds an artifact not only to a visible author name, but also to a structured generation context.

The Dynamic DNA Engine is designed for this purpose. It generates a human-readable, cryptographically anchored, and culturally meaningful provenance identifier for each significant artifact or action.

Unlike conventional content hashes, Dynamic DNA does not only summarize file content. It binds together:

dynamic_dna_inputs:

- creator identity
- claimed UID
- GPG fingerprint or public-key prefix
- timestamp
- cultural-temporal marker
- module name
- action type
- artifact digest
- audit route
- confirmation seal

This allows the resulting DNA string to serve as a compact entry point into the broader behavioral evidence chain.

The key design principle is:

A content hash proves that some bytes existed.

Dynamic DNA records who claimed the artifact, when, through which module, under which action, and under which audit route.

⸻

3.4.2 Design Goals

The Dynamic DNA Engine has seven design goals.

G1. Human-Readable Provenance

The identifier should be readable by ordinary users, not only by machines.

A conventional SHA-256 hash is technically useful but cognitively opaque. Dynamic DNA keeps the hash but wraps it inside a structured, human-readable format.

Example:

**龍芯⚡️2026-05-04-午时-金-BEHAVIORAL-VERIFY-A2D0092C-7FA3C91B**

This tells the user:

3.4.11 Security Analysis

Property 1: Artifact Binding

If the artifact changes, its SHA-256 digest changes. Therefore, the DNA record no longer verifies.

artifact ≠ artifact' => hash(artifact) ≠ hash(artifact')

Within standard cryptographic assumptions, collision probability is negligible.

Property 2: Identity Binding

The DNA string includes the UID and GPG prefix. The canonical record includes the full GPG fingerprint.

This does not prove signature validity by itself. It provides a structured identity claim that must be checked against a signature or trusted public record.

Property 3: Temporal Consistency

The DNA record includes ISO time, date, shichen, and digit root. A forged record must keep these fields mutually consistent.

This does not prevent a local attacker from creating a false timestamp unless the ledger is externally anchored. It does, however, increase inconsistency detection when combined with append-only logs.

Property 4: Lineage Continuity

Parent DNA links create a chain:

DNA_0 -> DNA_1 -> DNA_2 -> ... -> DNA_n

If an attacker removes or changes an intermediate record, the chain becomes inconsistent unless they can rewrite all subsequent anchored entries.

Property 5: Privacy Preservation

Only hashes and metadata need to be stored for sensitive content. The engine supports sealed and burn modes to avoid storing raw private text.

3.5 Evidence Ledger and Lineage Chain

3.5.1 Motivation

The Dynamic DNA Engine introduced in Section 3.4 creates a compact provenance root for individual artifacts or actions. However, provenance does not emerge from isolated identifiers. It emerges from continuity.

A single DNA record can show that one artifact was generated under a specific identity, time, module, and action. But content creation in human-AI collaboration is rarely a single-step process. It usually involves multiple revisions, model interactions, rule applications, persona routing decisions, corrections, mistakes, and re-exports.

Therefore, Behavioral Cryptography requires an append-only evidence ledger that records each significant action and links it to previous actions.

The central principle is:

A single DNA proves a point.

A ledger proves a path.

A lineage chain proves continuity.

In Chinese:

一个 DNA 是点；证据账本是线；血统链是路。

3.5.5 Lineage Chain Definition

Definition 3.5 — Evidence Ledger

An evidence ledger L is an ordered sequence of entries:

L = langle e_1, e_2, ..., e_n rangle

where each entry e_i contains:

e_i = langle dna_i, parent_i, action_i, time_i, hash_i, prevhash_i, audit_i rangle

Definition 3.6 — Lineage Chain

A lineage chain for artifact C_n is the ordered path:

Chain(C_n) = langle dna_0 rightarrow dna_1 rightarrow ... rightarrow dna_n rangle

where each dna_i is either the parent of dna_{i+1}, or is referenced through a valid ledger entry.

Definition 3.7 — Chain Continuity

A chain is continuous if:

1. Every non-root node has a valid parent_dna.
2. Every parent_dna exists in the ledger or in an accepted external checkpoint.
3. Timestamps are monotonic or explainably branched.
4. The ledger hash chain verifies.
5. No sealed or no_external record is exported without authorization.

3.5.7 Algorithm 5: Verify Ledger Integrity

def verify_ledger_integrity(ledger_path: Path) -> tuple[bool, list[str]]:

```python
evidence = []
if not ledger_path.exists():
    return False, ["Ledger file does not exist"]
previous_hash = "sha256:GENESIS"
line_no = 0
with ledger_path.open("r", encoding="utf-8") as f:
    for line in f:
        line_no += 1
        if not line.strip():
            continue
        try:
            entry = json.loads(line)
        except json.JSONDecodeError:
            return False, [f"Line {line_no}: invalid JSON"]
        recorded_previous = entry.get("previous_entry_hash")
        recorded_current = entry.get("current_entry_hash")
        if recorded_previous != previous_hash:
            return False, [
                f"Line {line_no}: previous hash mismatch",
                f"expected={previous_hash}",
                f"actual={recorded_previous}"
            ]
        entry_without_current = dict(entry)
        entry_without_current.pop("current_entry_hash", None)
        recomputed = compute_entry_hash(entry_without_current)
        if recomputed != recorded_current:
            return False, [
                f"Line {line_no}: current hash mismatch",
                f"expected={recomputed}",
                f"actual={recorded_current}"
            ]
        previous_hash = recorded_current
        evidence.append(f"Line {line_no}: verified {entry.get('entry_id')}")
return True, evidence
```

def verify_lineage_chain(

```python
ledger_path: Path,
target_dna: str,
allow_external_roots: bool = True
```

) -> tuple[bool, list[str]]:

```python
index = build_dna_index(ledger_path)
evidence = []
if target_dna not in index:
    return False, [f"Target DNA not found: {target_dna}"]
seen = set()
current = target_dna
while current:
    if current in seen:
        return False, [f"Cycle detected at {current}"]
    seen.add(current)
    entry = index.get(current)
    if not entry:
        if allow_external_roots:
            evidence.append(f"External root accepted: {current}")
            break
        return False, [f"Missing parent DNA: {current}"]
    evidence.append(f"DNA found: {current}")
    # Privacy rule check
    if entry.get("privacy_mode") == "sealed" and entry.get("retention") != "hash_only":
        return False, [f"Sealed record violates hash_only retention: {current}"]
    if entry.get("trace_mode") == "no_external" and entry.get("event", "").startswith("EXPORT"):
        return False, [f"no_external record exported illegally: {current}"]
    parent = entry.get("parent_dna")
    if not parent:
        evidence.append("Root reached")
        break
    current = parent
return True, evidence
```

3.5.11 Security Properties

Theorem 3.10 — Ledger Tamper Evidence

If any ledger entry e_i is modified after creation, then the hash verification for e_i or some later entry e_j fails.

Proof Sketch.

Each entry stores previous_entry_hash and current_entry_hash. The current hash is computed over the canonical entry content. Modifying an entry changes its computed hash. Since the next entry stores the previous hash, the mismatch propagates. ∎

Theorem 3.11 — Lineage Continuity

If every derived artifact contains a valid parent_dna, and every parent exists in the ledger or external checkpoint, then the artifact has a continuous lineage chain to a known root.

Proof Sketch.

Starting from the target DNA, repeatedly follow parent_dna. If each parent exists and no cycle appears, the chain terminates at a root or accepted checkpoint. ∎

Theorem 3.12 — Correction Preservation

Appending correction records preserves accountability better than overwriting prior records.

Proof Sketch.

Overwriting removes evidence of the previous state. Appending creates a new record that references the earlier record. The prior claim, the correction, and the reason remain available for audit. ∎

Theorem 3.13 — No Silent Laundering

If a content artifact is paraphrased or exported without a valid parent DNA, the ledger verification fails to establish continuous lineage.

Proof Sketch.

The exported artifact may have its own hash and DNA, but without a valid parent_dna chain, it cannot prove descent from the original source. ∎

3.6 Evaluation Protocol and Attack Simulation

3.6.1 Purpose of Evaluation

The purpose of the evaluation is to test whether Behavioral Cryptography can distinguish legitimate lineage from forged or laundered lineage under practical adversarial conditions.

Unlike conventional AI-detection benchmarks, the goal is not to determine whether an artifact was generated by a machine. The goal is to verify whether the claimed provenance chain is valid.

Therefore, our evaluation focuses on lineage integrity rather than generation origin.

The central evaluation question is:

Given a content artifact C and a claimed originator E, can the system determine whether C belongs to a continuous behavioral lineage rooted in E?

This reframes evaluation from:

Old question:

Was this written by AI?

New question:

Can this artifact prove its behavioral lineage?

⸻

The evaluation uses five classes of artifacts.

A1. Original Artifacts

These are legitimate outputs generated by UID9622 under the Longhun protocol.

original_artifacts:

direct_copies:

def weighted_geometric_mean(scores: List[float], weights: List[float]) -> float:

```python
if len(scores) != len(weights):
    raise ValueError("scores and weights must have the same length")
if any(s == 0.0 for s in scores):
    return 0.0
numerator = 1.0
for s, w in zip(scores, weights):
    numerator *= s ** w
return numerator ** (1.0 / sum(weights))
```

3.6.11 Failure Mode Analysis

Behavioral Cryptography should not pretend to solve everything.

Failure Mode 1: GPG Private Key Compromise

If the originator’s private key is compromised, F1 becomes unreliable.

Mitigation:

- key rotation
- revocation entry
- external checkpoint
- multi-signature backup
- device-bound signing policy

Failure Mode 2: Incomplete Ledger

If the user does not record actions consistently, lineage confidence decreases.

Mitigation:

- automatic append-only logger
- local JSONL ledger
- periodic checkpoint
- missing parent warning

Failure Mode 3: Overly Aggressive Protected Lexicon

If protected terms are too broad, legitimate paraphrases may be falsely rejected.

Mitigation:

- classify protected terms into critical / important / optional
- only critical terms trigger hard failure
- optional terms reduce confidence but do not reject

Failure Mode 4: Style Drift Over Time

A creator’s writing style may evolve.

Mitigation:

- use rolling baseline
- compare trajectory instead of single static vector
- do not rely on F6 alone

Failure Mode 5: Legitimate Anonymous Contribution

Some contributors may not want strong identity binding.

Mitigation:

- support pseudonymous DNA
- local-only proof bundle
- privacy-preserving hashes
- optional public disclosure

3.7.3 Core Component 1: Local-First Runtime

Purpose

The Local-First Runtime is the execution boundary of the system. It ensures that provenance verification can happen locally, without requiring the user to surrender raw content, private memory, drafts, keys, or sensitive artifacts to a centralized service.

This component is critical because Behavioral Cryptography is not only a verification framework; it is also a sovereignty-preserving framework.

Design Requirements

local_first_runtime:

default_mode: "local_only"

Runtime Rules

1. Raw content is processed locally by default.
2. Private keys are never read by the verifier.
3. Secrets, tokens, and private credentials trigger sealed mode.
4. External export requires explicit user action.
5. Failed verification does not delete evidence.
6. Every verification attempt writes an audit event.

Boundary Statement

The implementation does not require global cloud trust. A user can generate, verify, and export proof bundles locally. External services may assist in formatting or review, but they are not the root of trust.

信任根在本地，不在平台；平台可以看证明包，不能拿走根。

def digit_root_from_text(text: str) -> int:

```python
digits = [int(ch) for ch in text if ch.isdigit()]
if not digits:
    return 0
n = sum(digits)
while n >= 10:
    n = sum(int(ch) for ch in str(n))
return n
```

def get_shichen(dt: datetime) -> str:

```python
hour = dt.hour
index = ((hour + 1) % 24) // 2
```

def sha256_text(text: str) -> str:

```python
return hashlib.sha256(text.encode("utf-8", errors="ignore")).hexdigest()
```

```python
wuxing = DIGIT_ROOT_TO_WUXING[dr]
nonce = secrets.token_hex(4).upper()
dna_hash = sha256_text(f"{seed}|{nonce}")[:8].upper()
dna = f"#龍芯⚡️{date_str}-{shichen}时-{wuxing}-{module.upper()}-{dna_hash}"
return {
    "dna": dna,
    "uid": uid,
    "gpg_fingerprint": gpg_fingerprint,
    "gpg_prefix": gpg_fingerprint[:8].upper(),
    "iso_time": iso_time,
    "shichen": f"{shichen}时",
    "digit_root": dr,
    "wuxing": wuxing,
    "module": module,
    "action": action,
    "content_hash": f"sha256:{content_hash}",
    "nonce": nonce,
    "confirm": confirm,
    "seal": seal
}
```

Important Boundary

The DNA string itself is not a replacement for a cryptographic signature. It is a provenance identifier. Strong authenticity requires either:

DNA + content_hash + ledger continuity + GPG signature

or:

DNA + proof bundle + external checkpoint

DNA 是身份证号，不是私钥本身；要抗伪造，必须接 hash、GPG、账本链。

def load_last_entry_hash(ledger_path: Path) -> str:

```python
if not ledger_path.exists():
```

```python
clean_entry = dict(entry)
```

def append_ledger_event(ledger_path: Path, event: dict) -> dict:

```python

    "timestamp": event.get("timestamp", now_iso()),
    "previous_entry_hash": previous_hash
}

    f.write(json.dumps(entry, ensure_ascii=False) + "\n")
```

Ledger Integrity Verification

def verify_ledger_integrity(ledger_path: Path) -> tuple[bool, list]:

```python
errors = []
previous_hash = "GENESIS"
if not ledger_path.exists():
    return False, ["Ledger file does not exist"]
with ledger_path.open("r", encoding="utf-8") as f:
    for line_no, line in enumerate(f, start=1):
        if not line.strip():
            continue
        entry = json.loads(line)
        if entry.get("previous_entry_hash") != previous_hash:
            errors.append({
                "line": line_no,
                "error": "previous_entry_hash mismatch"
            })
        expected_hash = compute_entry_hash(entry)
        if entry.get("current_entry_hash") != expected_hash:
            errors.append({
                "line": line_no,
                "error": "current_entry_hash mismatch"
            })
        previous_hash = entry.get("current_entry_hash")
return len(errors) == 0, errors
```

not the content itself.

能证明“我处理过”，不等于要保存“我看过什么”。

3.8 Limitations and Governance Considerations

3.8.1 Overview

Behavioral Cryptography is designed to strengthen provenance verification in human-AI collaborative content production. However, it should not be interpreted as an absolute authorship oracle, a legal adjudication mechanism, or a surveillance infrastructure.

The framework improves evidence quality by combining identity, time, rule traces, persona routes, protected lexicon, style vectors, and mistake ledgers. Yet each of these factors has limits. Cryptographic identifiers can be lost or compromised. Style vectors can be noisy. Mistake ledgers can be incomplete. Local ledgers can be tampered with unless externally checkpointed. Cultural-temporal markers improve recognizability and forgery cost but do not replace formal cryptographic signatures.

Therefore, this section clarifies the limitations, governance risks, privacy boundaries, and ethical constraints of Behavioral Cryptography.

The central governance principle is:

provenance verification must protect creator sovereignty without becoming a tool for surveillance, exclusion, or institutional capture.

追溯是为了保护创作者，不是为了把人关进平台的笼子里。

⸻

Dynamic DNA provides a structured provenance identifier. It binds together UID, timestamp, cultural-temporal markers, module information, action type, content hash, and system metadata.

A DNA string can show identity intent and provenance structure, but strong authenticity requires additional evidence:

- GPG fingerprint or signature;
- content hash;
- ledger history;
- parent-child lineage;
- timestamp consistency;
- protected lexicon preservation;
- evidence bundle integrity.

Paper-ready statement

Dynamic DNA should be understood as a provenance identifier rather than a standalone cryptographic signature. Its evidentiary strength emerges only when combined with content hashes, append-only ledger entries, external checkpoints, and optional GPG signatures.

DNA 是门牌号，不是房产证；要证明归属，还要 hash、账本、签名和链路。

3.8.3 Limitation 2: Local Ledgers Are Tamper-Evident, Not Globally Tamper-Proof

It does not provide:

global immutability

- trusted timestamp authorities;

- multi-party witness logs.

The local ledger is tamper-evident but not globally tamper-proof. Stronger non-repudiation requires periodic external checkpoints, such as public hash publication, notarization, or multi-party witness mechanisms.

3.9 Discussion: From Machine Detection to Lineage Verification

3.9.1 The Wrong Question: “Was This Generated by AI?”

Most current approaches to AI content authentication begin with a narrow question:

Was this content generated by a machine?

This question was useful in the early phase of generative AI, when the main concern was distinguishing human-written text from machine-generated text. However, it becomes increasingly inadequate as human-AI collaboration becomes the default mode of knowledge production.

In real-world workflows, content is rarely produced by one pure source. A single artifact may involve:

- human-originated concepts;
- AI-assisted drafting;
- AI-assisted translation;
- human correction;
- platform formatting;
- citation reconstruction;
- legal redaction;
- style polishing;
- multi-model comparison;
- final human approval.

In such a setting, asking whether the content was “AI-generated” collapses a complex process into a misleading binary.

The more important question is:

Who originated the core idea, which systems helped transform it, which rules governed the transformation, and what evidence remains?

This is the central shift introduced by Behavioral Cryptography.

“是不是 AI 写的”这个问题太浅。真正要问的是：根是谁的，链怎么走的，谁负责，证据在哪。

⸻

3.9.2 Why Detection Is Not Enough

AI detection methods typically rely on statistical signals, watermarking, metadata, or platform-side provenance records. These methods can help identify certain synthetic artifacts, but they face structural limitations.

First, statistical detectors are fragile under paraphrasing, translation, editing, and multi-model laundering. Once text is rewritten across several models or manually polished, the surface signal changes.

Second, watermarking systems often require cooperation from model providers. If the model does not watermark output, or if the content is transformed after generation, detection becomes unreliable.

Third, metadata-based approaches are platform-dependent. They work only when the relevant software pipeline preserves metadata and when downstream platforms respect it.

Fourth, detection usually focuses on origin at the level of generation, not lineage at the level of decision-making.

Behavioral Cryptography does not reject detection. Instead, it argues that detection is only one layer. A provenance framework must also verify:

- identity anchoring;
- time anchoring;
- rule history;
- persona routing;
- protected terminology;
- style continuity;
- mistake and correction history;
- ledger continuity;
- export boundaries;
- governance constraints.

Paper-ready statement

Detection asks whether a machine produced the surface artifact. Lineage verification asks whether the artifact belongs to a verifiable chain of human intention, AI assistance, procedural rules, corrections, and evidence.

检测看表面，血统链看过程。

⸻

3.9.3 Human-AI Collaboration Requires Process Integrity

Human-AI collaboration changes the meaning of authorship.

In traditional writing, authorship was often inferred from final text, drafts, timestamps, and publication history. In AI-assisted writing, final text alone becomes much less informative. Multiple people can ask similar prompts. Multiple models can generate similar phrasing. A polished final output may hide a long chain of human decisions.

Therefore, authorship must be understood as process integrity.

Process integrity means that the artifact can be traced through:

Human intent

→ prompt / instruction

→ AI assistance

→ human selection

→ rule-based correction

→ revision history

→ evidence ledger

→ final publication

Behavioral Cryptography captures this process through a multi-factor lineage model.

Key claim

- F3 missing;

The attacker rewrites the content using a language model while preserving the general meaning.

- F3/F4/F7 likely missing;

5.4.1 Composite Confidence

The primary score is the composite confidence:

conf(Sigma)=left(prod_{i=1}^{7} score_i^{w_i}right)^{1/sum w_i}

weights:

F1_identity_dna: 0.25

F2_temporal_anchor: 0.15

F3_rule_trace: 0.15

F4_persona_route: 0.12

F5_protected_lexicon: 0.12

F6_style_vector: 0.11

F7_mistake_ledger: 0.10

Hard failure rule:

```python
conf = 0.0
```

5.4.2 Attack Detection Rate

ADR = frac{text{detected attacked artifacts}}{text{total attacked artifacts}}

An attack is considered detected if:

conf < threshold

evidence log contains critical mismatch

Recommended thresholds:

thresholds:

legitimate_accept: conf >= 0.85

manual_review: 0.50 <= conf < 0.85

reject_or_flag: conf < 0.50

def evaluate_behavioral_cryptography(originals, attack_generators, verifier):

```python
results = []
for artifact in originals:
    proof_bundle = build_proof_bundle(artifact)
    # Evaluate legitimate artifact
    legit_result = verifier.verify(artifact, proof_bundle)
    results.append({
        "artifact_id": artifact.id,
        "variant": "original",
        "attack": None,
        "conf": legit_result.conf,
        "hard_failure": legit_result.hard_failure,
        "evidence": legit_result.evidence.summary()
    })
    # Evaluate attacked variants
    for attack_name, attack_fn in attack_generators.items():
        attacked = attack_fn(artifact)
        attacked_result = verifier.verify(attacked, proof_bundle)
        results.append({
            "artifact_id": artifact.id,
            "variant": "attacked",
            "attack": attack_name,
            "conf": attacked_result.conf,
            "hard_failure": attacked_result.hard_failure,
            "evidence": attacked_result.evidence.summary()
        })
return summarize_results(results)
```

Some factor scores rely on implementation choices, such as semantic similarity thresholds or style-vector embeddings. Different models may yield different scores.

Behavioral lineage is not identical to legal authorship. The framework provides evidence, not automatic legal judgment.

Operational Validity

If local logs are lost, corrupted, or never generated, provenance strength decreases.

We evaluate Behavioral Cryptography as a lineage verification framework rather than an AI-generation detector. The goal is to determine whether a content artifact can be linked to a claimed originator through a multi-factor evidence chain under common laundering attacks.

6.1 Motivation: From Local Proof to Shared Standard

The evaluation in Chapter 5 demonstrates that Behavioral Cryptography can provide structured evidence for lineage verification under common laundering attacks. However, a provenance framework becomes socially meaningful only when its evidence can be interpreted beyond a single local system.

This chapter describes a governance and standardization pathway for Behavioral Cryptography. The goal is not to replace existing provenance infrastructures such as cryptographic signatures, content credentials, or institutional audit systems. Instead, Behavioral Cryptography adds a creator-controlled behavioral lineage layer that can interoperate with them.

The central governance question is:

How can an individual creator preserve authorship lineage, disclose AI collaboration, protect private evidence, and remain compatible with public provenance standards?

Behavioral Cryptography answers this through four principles:

4. Interoperability — the framework can coexist with GPG, C2PA-style metadata, local audit logs, and future institutional registries.

7.1 Conclusion

The central problem addressed in this paper is not whether a piece of content was generated by a machine. In the age of human-AI collaboration, that question has become increasingly insufficient. AI assistance may appear in drafting, translation, editing, formalization, coding, formatting, or critique. Copying content is easy. Copying lineage is hard.

Surface text can be paraphrased, translated, polished, or laundered through multiple AI systems. However, the full behavioral lineage of a work — its identity anchor, temporal sequence, rule history, collaborative route, protected vocabulary, stylistic continuity, and honest correction record — is substantially harder to forge in full.

Behavioral Cryptography therefore reframes content authentication from machine detection to lineage verification.

A.3 Utility Functions

def sha256_text(text: str) -> str:

```python
return hashlib.sha256(text.encode("utf-8", errors="ignore")).hexdigest()
```

def weighted_geometric_mean(scores: List[float], weights: List[float]) -> float:

```python
if len(scores) != len(weights):
    raise ValueError("scores and weights must have equal length")
if any(s == 0.0 for s in scores):
    return 0.0
total_weight = sum(weights)
product = 1.0
for s, w in zip(scores, weights):
    product *= s ** w
return product ** (1.0 / total_weight)
```

def cosine_similarity(a: List[float], b: List[float]) -> float:

```python
if len(a) != len(b) or len(a) == 0:
    return 0.0
dot = sum(x * y for x, y in zip(a, b))
norm_a = math.sqrt(sum(x * x for x in a))
norm_b = math.sqrt(sum(y * y for y in b))
if norm_a == 0.0 or norm_b == 0.0:
    return 0.0
return dot / (norm_a * norm_b)
```

def is_monotonic_timestamps(items: List[Dict[str, Any]]) -> bool:

```python
times = []
for item in items:
    ts = item.get("timestamp")
    if not ts:
        return False
    try:
        times.append(datetime.fromisoformat(ts))
    except Exception:
        return False
return all(times[i] <= times[i + 1] for i in range(len(times) - 1))
```

```python
    evidence.add(
        "COMPOSITE",
        0.0,
        "FAIL",

        scores=scores
    )

weights = [0.25, 0.15, 0.15, 0.12, 0.12, 0.11, 0.10]
conf = weighted_geometric_mean(scores, weights)
evidence.add(
    "COMPOSITE",
```
