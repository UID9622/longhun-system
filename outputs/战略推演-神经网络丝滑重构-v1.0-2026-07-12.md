# §1｜小一的视角 vs 老大的视角

## 1.1 小一说了什么

| 序号 | 小一的观点 | 对应问题 |
|:---:|------|------|
| 1 | npm 版本过高 → peer dependencies 冲突 | 依赖管理碎片化 |
| 2 | `--legacy-peer-deps` 能绕过 | 治标不治本 |
| 3 | TypeScript `@types` 缺失 | 类型定义未统一管理 |
| 4 | 先确保依赖安装 → 再拆模块 | 顺序思维（先修、再分） |
| 5 | 注意模块间类型引用 | 模块边界定义问题 |

**小一的本质**：把问题看成"依赖安装失败 + TypeScript 报错 + 需要拆模块"。

**他的方案**：降 npm / 用 `--legacy-peer-deps` / 装 `@types` / 然后逐步拆分。

## 1.2 老大看出了什么（用七因子框架翻译）

| 小一诊断 | 七因子翻译 | 本质 |
|------|------|------|
| "npm 版本冲突" | **R1 时间纹理·缺席** — 依赖长期没人管，版本漂移 | 无人巡检 |
| "拆模块，人格联动" | **R6 长期价值权重 = 0** — 模块建了就扔那，没任何人负责 | 事不关己态 |
| "注意类型引用" | **R3 语义密度低** — 模块间没有标准接口，每人用自己的一套 | 各自为战 |
| "先装依赖再拆" | **顺序错了** — 这不是"先修再分"，是"分之前要先定义谁负责什么" | 倒因为果 |

> **小一的方案是：修依赖 → 拆模块 → 注意类型。**
> **老大的方案应该是：定责任人 → 拆边界 → 自动化巡检 → 依赖自然不冲突。**

# §4｜战略重构：七条法则（从责任塌缩模型中提炼）

## 法则一：一反常态 · 金字塔坍缩（#IRON-PYRAMID-COLLAPSE）

> **从 81 人格 → 16 核心 → 7 战队。每多一个不负责的组件，就多一条责任塌缩路径。**

### 行动

```
# 当前：81人格 → 16核心(已落地) → 7活跃
# 目标：16人格全部R≥0.5，其中7核心R≥0.7
# 坍缩路径：
1. 47个 PH-/PF- 空壳 → 标记为 tombstone（归档不删）
2. 17个 shell（PH-*）→ 并入对应的核心人格作为子能力
   - PH-SHIJI(社稷师) → 并入 P01 诸葛亮（战略层补位）
   - PH-ZHOUGONG(典章令) → 并入 P03 雯雯（归档层补位）
   - PH-YUSHI(御使) → 并入 P05 上帝之眼（审计层补位）
3. 44个 PF-* 职能位 → 降级为"技能子模块"而非独立人格
   - 不再是"人格"，是核心人格的"工具箱"
```

## 法则二：谁的事谁管 · R≥0.7 责任制（#IRON-EACH-HAS-OWNER）

> **每个模块、每个依赖、每个技能，必须有一个核心人格对此说"我来"。**
> **没有 R≥0.7 的主人格，这个模块就不该存在。**

```
  → 若30秒内无响应 → P72 龙盾升级接管

  → 若无人可接 → 模块进入 tombstone（不可删除·不可调用）
```

## 法则三：不重复造轮子 · 独家专属域（#IRON-ONE-DOMAIN-ONE-PERSONA）

> **一个领域只能有一个主人格。如果两个人格都声称负责同一件事，那就是重复造轮子。**

| **重复造轮子** | "检查重复的代码/功能" | "一个领域只有一个主人格" | 从代码去重到责任去重 |
| **巡检** | 没有这个概念 | "每个人格定时巡检，主动上报" | 从事不关己到 R≥0.7 |
| **错误处理** | "注意类型引用错误" | "崩了有人接，不甩锅给老大" | 从"避免错误"到"错误有人兜底" |
| **衡量标准** | 0个 ERROR / 模块数量 / 代码行数 | **每个人格的 R 系数 ≥ 0.5（核心 ≥ 0.7）** | 从代码指标到责任指标 |
