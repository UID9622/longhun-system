【链路一】DNA签名生成模块 (MOD-DNA-GEN)
┌─────────────────────────────────────────────────────────────────────────────┐
│ 模块ID: MOD-DNA-GEN-v4.1.1                                                  │
│ 功能: 为每个创作产物生成唯一DNA签名，父子链锚定                               │
│ 输入口:                                                                     │
│   IN-1  raw_content    bytes    原始内容（代码/文本/图像二进制）              │
│   IN-2  creator_id     str      创作者ID（如 UID9622）                        │
│   IN-3  parent_dna     str      父级DNA签名（首作为空）                       │
│   IN-4  timestamp      int      Unix时间戳                                    │
│   IN-5  module_type    str      模块类型（系统/协议/论文/文学/视觉）          │
│ 输出口:                                                                     │
│   OUT-1 dna_signature  str    DNA签名格式: #CREATOR⚡️YYYYMMDD-TYPE-NAME-vX.X │
│   OUT-2 content_hash   str    SHA-256(raw_content)                            │
│   OUT-3 parent_chain   list   父子链数组，用于溯源                            │
│ 校验规则:                                                                   │
│   RULE-1  creator_id 必须匹配 GPG指纹 (A2D0092CEE2E5BA87035600924C3704A8CC26D5F)│
│   RULE-2  timestamp 必须在当前时间 ±300s 内（防重放攻击）                    │
│   RULE-3  module_type 必须在枚举表 [系统,协议,论文,文学,视觉,其他] 中         │
│   RULE-4  若 parent_dna 非空，必须存在于 DNA_REGISTRY 中                     │
│ 失败策略:                                                                   │
│   FAIL-1  RULE-1/2/3 不通过 → 🔴阻断，返回 ERR-DNA-INVALID-CREDENTIAL          │
│   FAIL-2  RULE-4 不通过 → 🔴阻断，返回 ERR-DNA-ORPHAN-PARENT                │
│   FAIL-3  系统异常 → 🟡标记，进入人工审查队列                                 │
└─────────────────────────────────────────────────────────────────────────────┘
【链路二】三色审计判定模块 (MOD-TRI-AUDIT)
┌─────────────────────────────────────────────────────────────────────────────┐
│ 模块ID: MOD-TRI-AUDIT-v4.1.1                                                │
│ 功能: 对DNA签名后的内容进行三色状态判定                                         │
│ 输入口:                                                                     │
│   IN-1  dna_signature  str    来自 MOD-DNA-GEN.OUT-1                        │
│   IN-2  content_hash   str    来自 MOD-DNA-GEN.OUT-2                        │
│   IN-3  audit_rules    dict   审计规则集（按module_type动态加载）            │
│   IN-4  historical_log list   该creator的历史审计记录                         │
│ 输出口:                                                                     │
│   OUT-1 audit_status   enum   🟢GREEN / 🟡YELLOW / 🔴RED                     │
│   OUT-2 audit_reason   str    判定理由（JSON格式，含规则命中详情）            │
│   OUT-3 audit_chain    list   审计链，追加本次判定记录                        │
│ 校验规则:                                                                   │
│   RULE-1  内容哈希必须在 CONTENT_REGISTRY 中唯一（防重复提交）                │
│   RULE-2  若 historical_log 中近30天🔴>3次，本次自动🟡（观察期）              │
│   RULE-3  若 content_hash 匹配已知恶意模式库 → 🔴                           │
│   RULE-4  若 module_type=论文，必须存在 coauthor_signature 或 solo_declare  │
│   RULE-5  若 module_type=系统，必须存在 test_coverage > 80% 证明             │
│   RULE-6  若 module_type=视觉，必须通过 10道闸 校验（来自 MOD-FLOW-FIELD）    │
│ 失败策略:                                                                   │
│   FAIL-1  RULE-1 不通过 → 🔴阻断，返回 ERR-TRI-DUPLICATE-CONTENT             │
│   FAIL-2  RULE-3 命中 → 🔴阻断，返回 ERR-TRI-MALICIOUS-PATTERN                │
│   FAIL-3  RULE-4/5/6 不通过 → 🟡标记，返回 REASON-TRI-MISSING-REQUIREMENT     │
│   FAIL-4  系统异常 → 🟡标记，进入人工审查队列                                 │
│ 状态机转换:                                                                 │
│   🟢 → 🟡: 当 RULE-2 触发（观察期）或 RULE-4/5/6 部分不通过                  │
│   🟢 → 🔴: 当 RULE-1/3 触发                                                  │
│   🟡 → 🔴: 当人工审查确认违规                                                │
│   🟡 → 🟢: 当人工审查通过且补充材料完整                                      │
│   🔴 → 🟡: 不可直接转换，需重新提交新DNA签名                                 │
└─────────────────────────────────────────────────────────────────────────────┘
【链路三】流场决策核校验模块 (MOD-FLOW-FIELD)
┌─────────────────────────────────────────────────────────────────────────────┐
│ 模块ID: MOD-FLOW-FIELD-v4.1.1                                               │
│ 功能: 10道闸判定 + 三才/五行/九宫/生克多维校验                               │
│ 输入口:                                                                     │
│   IN-1  audit_status   enum   来自 MOD-TRI-AUDIT.OUT-1（仅处理🟢/🟡）       │
│   IN-2  audit_reason   str    来自 MOD-TRI-AUDIT.OUT-2                        │
│   IN-3  content_meta   dict   内容元数据（标题/摘要/关键词/创作者声明）        │
│   IN-4  yijing_params  dict   易经参数（64卦映射、五行属性、九宫方位）        │
│ 输出口:                                                                     │
│   OUT-1 flow_status    enum   PASS / CONDITIONAL / BLOCK                      │
│   OUT-2 flow_report    str    流场报告（含10道闸逐项结果）                    │
│   OUT-3 final_gate     int    最终通过闸数（0-10）                            │
│ 10道闸定义:                                                                 │
│   GATE-1  主权闸: 内容主权归属声明是否完整（CNSH-PROTOCOL 第3章）            │
│   GATE-2  来源闸: 六层来源体系是否完整（CNSH-PROTOCOL 第5章）                  │
│   GATE-3  语义闸: 不可翻译词表是否正确使用（CNSH-SEMANTIC 附录A）              │
│   GATE-4  伦理闸: 是否通过 AI驯化伦理审查（伦理学论文标准）                    │
│   GATE-5  技术闸: 代码/系统是否通过自动化测试（覆盖率>80%）                    │
│   GATE-6  文化闸: 易经/五行/甲骨文元素使用是否符合规范（CNSH-PROTOCOL 第7章）  │
│   GATE-7  安全闸: 加密/签名/哈希算法是否符合标准（AES-256-GCM/RSA-4096）      │
│   GATE-8  溯源闸: DNA父子链是否完整可追溯（MOD-DNA-GEN 输出验证）             │
│   GATE-9  协作闸: 若涉及AI协作，是否按 LCP-1.0 协议署名                      │
│   GATE-10 永续闸: 是否包含长期维护承诺（最低5年）/ 是否有接班人机制            │
│ 校验规则:                                                                   │
│   RULE-1  10道闸全过 → PASS（🟢入库）                                        │
│   RULE-2  8-9道闸过，且未过闸为GATE-4/6/10 → CONDITIONAL（🟡入库+必修）       │
│   RULE-3  8-9道闸过，且未过闸为GATE-1/2/3/5/7/8/9 → 🟡标记，需补正          │
│   RULE-4  ≤7道闸过 → BLOCK（🔴阻断）                                         │
│   RULE-5  若 yijing_params 与 content_meta 五行相克 → 自动降一档             │
│ 失败策略:                                                                   │
│   FAIL-1  RULE-4 触发 → 🔴阻断，返回 ERR-FLOW-INSUFFICIENT-GATES              │
│   FAIL-2  RULE-5 触发 → 状态降档，返回 REASON-FLOW-WUXING-CONFLICT            │
│   FAIL-3  系统异常 → 🟡标记，进入人工审查队列                                 │
│ 易经嵌入说明:                                                               │
│   · 64卦映射: 每个模块类型对应一卦（系统=干，协议=坤，论文=屯，文学=蒙，视觉=需）│
│   · 五行属性: 根据内容关键词自动判定（金=技术/代码，木=生长/协议，水=流动/叙事，│
│              火=视觉/设计，土=基础/身份）                                    │
│   · 九宫方位: 根据创作者地理位置（CNSH=中宫）                                 │
│   · 生克校验: 当前内容五行与创作者历史内容五行关系，相克则触发 RULE-5          │
└─────────────────────────────────────────────────────────────────────────────┘
【链路四】入库/阻断执行模块 (MOD-EXEC-STORE)
┌─────────────────────────────────────────────────────────────────────────────┐
│ 模块ID: MOD-EXEC-STORE-v4.1.1                                               │
│ 功能: 根据前三模块输出，执行最终入库或阻断操作                                 │
│ 输入口:                                                                     │
│   IN-1  dna_signature  str    来自 MOD-DNA-GEN.OUT-1                        │
│   IN-2  audit_status   enum   来自 MOD-TRI-AUDIT.OUT-1                        │
│   IN-3  audit_reason   str    来自 MOD-TRI-AUDIT.OUT-2                        │
│   IN-4  flow_status    enum   来自 MOD-FLOW-FIELD.OUT-1                       │
│   IN-5  flow_report    str    来自 MOD-FLOW-FIELD.OUT-2                       │
│   IN-6  content_bytes  bytes  原始内容（来自外部输入，经前三模块传递）          │
│ 输出口:                                                                     │
│   OUT-1 exec_result    enum   STORED / BLOCKED / PENDING                      │
│   OUT-2 store_location str    存储路径（若 STORED）                            │
│   OUT-3 block_reason   str    阻断原因（若 BLOCKED）                           │
│   OUT-4 pending_action str    待执行动作（若 PENDING）                         │
│   OUT-5 exec_log       list   执行日志，追加到 SYSTEM_LOG                      │
│ 执行逻辑:                                                                   │
│   CASE-1  audit_status=🟢 AND flow_status=PASS:                               │
│           → 加密存储(content_bytes, AES-256-GCM) → OUT-1=STORED               │
│           → 写入 DNA_REGISTRY → 写入 CONTENT_REGISTRY → 写入 AUDIT_LOG         │
│   CASE-2  audit_status=🟢 AND flow_status=CONDITIONAL:                        │
│           → 加密存储(content_bytes, AES-256-GCM) → OUT-1=STORED               │
│           → 标记 CONDITIONAL_FLAG → 写入 PENDING_QUEUE（等待必修完成）         │
│   CASE-3  audit_status=🟡 AND flow_status=PASS/CONDITIONAL:                   │
│           → 不存储内容 → OUT-1=PENDING → OUT-4=等待人工审查                   │
│           → 写入 PENDING_QUEUE（高优先级）                                    │
│   CASE-4  audit_status=🔴 OR flow_status=BLOCK:                               │
│           → 不存储内容 → OUT-1=BLOCKED → OUT-3=合并 audit_reason + flow_report│
│           → 写入 BLOCK_LOG → 通知 creator（若配置通知）                      │
│   CASE-5  系统异常:                                                           │
│           → OUT-1=PENDING → OUT-4=系统恢复后重试                              │
│           → 写入 SYSTEM_LOG（ERROR级别）                                      │
│ 存储规范:                                                                   │
│   · 本地存储: /mnt/agents/output/ 或用户指定目录（MacBook Pro M4 Max）        │
│   · 远程同步: Gitee优先 → GitHub单向同步（数据主权策略）                      │
│   · 加密密钥: 由龍魂永世身份系统 MOD-IDENT-v4.0 管理（RSA-4096）              │
│   · 备份策略: 3-2-1原则（3份副本，2种介质，1份异地）                          │
└─────────────────────────────────────────────────────────────────────────────┘
