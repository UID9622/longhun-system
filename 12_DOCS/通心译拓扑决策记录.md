## 📜 一、背景：为什么从平面 19 出发

通心译总台（Notion database `60fb0bb0-2482-4a6e-b9e3-8ae08d010a65`）有 **19 条行资产**，
分布在 6 个层（核心ASI层 / 执行Agent层 / 技能库 / 文档库 / 系统架构层 / 工具层）。

**19 是"行"级的事实**：每行代表总台里登记的一件资产（页面或数据库的引用行）。
过去 verify/stats/root_hash 全部以 19 为节点数，因为拓扑只有一层。

**为什么需要升级**：总台里存在"行资产指向的库本体"——数据库本体（database）是独立实体，
有自己的一行行数据、有自己的父页面、有自己的更新时间。平面 19 只记录了"总台提到过它"，
没有记录"它本身是什么、有多少行、父页面是谁"。图谱要诚实，就得把这一层补上。

**但补层的度，由下面的三条决策定义。**

## 📜 二、决策一：为什么只归集 2 个关联库（不把 404 硬算进来）

### 2.1 探测方法（实测）

对总台 19 行资产的每一个 URL/ID 目标做 **逐行探测**（Notion API）：

| 目标类型 | 数量 | 结果 |
|:---|:---:|:---|
| 行资产 URL 指向的真实目标 | 19 | 逐个解析 UUID → 调 API 判定是 page 还是 database |
| 命中为 page 的目标 | 11 | 递归 `query children` 展开，查其中是否内嵌 database |
| 命中为 database 的目标 | 待定 | 读行数、父页面、创建/编辑时间 |
| 跨 workspace 目标 | 1 | 记错本 `b498c4e0-…` → **404** |

### 2.2 归集标准（判定公式）

> **关联库入图 ⟺ 同时满足：**
> ① 目标是 **database 本体**（不是 page 枢纽）；
> ② 由总台某条行资产 **URL 直接指向、API 可达**；
> ③ 库本体数据完整可读（行数/父页/时间戳），DNA 可确认。

### 2.3 结果

| 关联库 | database_id | 行数 | 父页面 | 入图 |
|:---|:---|:---:|:---|:---:|
| 🌍 国家模板总库 v1.0 | `1d6a3cab-0c9a-420f-9de8-691164b267d3` | 38 | 💮 通心译·产品中心 `3b87125a-…` | ✅ 🟢 数据底座 |
| ③ 对话记忆库 ChatMemory | `32a7125a-9c9f-81d7-a6df-d71a2f6606e6` | 2 | 💰 产品设计稿 PRD `3297125a-…` | ✅ 🟡 PRD内嵌 |
| 📝 通心译·记错本 | `b498c4e0-…` | — | — | ❌ 不入图 |

### 2.4 为什么记错本不入图（404 不硬算）

记错本行资产指向的数据库，用当前 workspace token 调 `GET /v1/databases/{id}` 返回 **404**。
证据表明它是**跨 workspace** 的库（旧集成归属），当前凭据不可达。

三个处理选项及裁决：

| 选项 | 做法 | 裁决 |
|:---|:---|:---|
| A. 硬算入图 | 把 404 库注册为子图谱节点，状态标 🟡 | ❌ **否决**。节点必须经 verify 可验证（DNA+状态+链接）。不可达实体挂上去 = 造假实体 = 堆数量 |
| B. 删除该行 | 从总台移除记错本 | ❌ **否决**。违反「不删除只冻结」。总台确实引用了它，行资产是事实 |
| C. 冻结留档 | 行资产保持 🟡 待命；不入子图谱；探测证据留档 | ✅ **采纳**。行（资产视图）与库（本体视图）分离，各按各的事实入图 |

> 决策原则一句话：**可达才入图，404 留证据。** 图是事实的快照，不是愿望清单。

### 2.5 为什么 page 枢纽不重复归集

产品中心 `3b87125a-…`、系统文档集 `34d7125a-…` 等是 **page（页面枢纽）**，不是 database 本体。
递归展开 children 后，其中内嵌的可达 database 仅上述 2 个。
页面枢纽本身已被 19 行资产覆盖（它们就是行），再以「子图谱」身份入图 = 同一实体出现两次 = 双计膨胀。

## 📜 三、决策二：为什么 Obsidian 只取 1 个笔记（不全量导入）

### 3.1 实测环境

本地 Obsidian 库 = `~/Obsidian/龍魂系統/`（917 个 .md，龍魂系统早期镜像副本）。

### 3.2 关键词「通心译」全库扫描命中（实测）

| 文件 | 行数 | 性质 | 裁决 |
|:---|:---:|:---|:---|
| `NOTION_EXTRACTION_COMPLETE.md` | 325 | Notion 全量提取**完成报告**（🟢 完成·代码已提交·DNA `#龍芯⚡️2026-06-03-NOTION-EXTRACTION-COMPLETE-v1.0`） | ✅ 入图 · 知识资产 |
| `EditorChats/vscode_chat_f4b9d7db-….md` | 28,889 | **编辑器会话导出**（过程记录） | ❌ 默认排除 |
| `EditorChats/vscode_copilot_f4b9d7db-….md` | 1,616 | **编辑器会话导出**（过程记录） | ❌ 默认排除 |

### 3.3 判定标准

> **镜像笔记入图 ⟺ 是知识资产**：有独立知识价值 + 与图谱主题直接相关 + DNA 可溯。
> **过程记录默认排除**：聊天/会话导出、编辑器记忆属于"流水"，不是"知识"。

### 3.4 三个处理选项及裁决

| 选项 | 做法 | 裁决 |
|:---|:---|:---|
| A. 全量导入 917 | 整个旧镜像全部注册 | ❌ **否决**。917 里绝大多数是代码/缓存/聊天/重复镜像。把仓库当知识库扫 = 节点爆炸 = 堆数量 |
| B. 收全部 3 个命中 | 含 EditorChats | ❌ **否决**。28,889 行的会话导出既非知识资产也无法做知识校验，挂进图谱稀释可信度 |
| C. 只收知识资产 | 默认收 1 个（完成报告） | ✅ **采纳**。EditorChats 留 `--chats` 显式开关，需要时可收回，不默认混入 |

### 3.5 为什么还保留"镜像"概念

Obsidian 是**本地离线副本**。图谱挂 `📓 Obsidian·通心译 镜像` 子图谱节点（kind=obsidian-mirror），
意义不在"多一个节点"，而在**链路**：Notion 线上资产 ⟷ 本地镜像副本 ⟷ 本地文件路径（`file://` 可直达打开）。
知识主权归本地，云端断了本地还在。后续笔记变动走 `lh topo obsidian sync --name 通心译` 整体更新，不逐条堆。

## 📜 四、决策三：分层计数的设计依据

### 4.1 为什么要分层（平面 19 的局限）

总台是"行"的世界，但它指向的世界有三层真实结构：

```
🌐 通心译军团·总台（总台库 60fb0bb0 · 19 行资产）
├─ 🎯 核心ASI层  ×5     ← 行资产（组）
├─ 🤖 执行Agent层 ×1
├─ ⚡ 技能库     ×2
├─ 📚 文档库     ×5
├─ 🏗️ 系统架构层 ×4
├─ 🔧 工具层     ×2
└─ 🗄️ 子图谱（本体层 · 行资产指向的库/镜像）
   ├─ 🌍 国家模板总库 v1.0     [notion-db]       38 行
   ├─ ③ 对话记忆库 ChatMemory  [notion-db]        2 行
   └─ 📓 Obsidian·通心译 镜像   [obsidian-mirror]
      └─ NOTION_EXTRACTION_COMPLETE.md（笔记资产 ×1）
```

平面 19 把"行"当全部，子图谱层完全没有存在感。分层不是为好看，是**图谱必须反映实体真实结构**。

### 4.2 计数规则（iter_nodes 单一真相源）

`08_BIN/lh_topo.py` v1.5 引入统一节点遍历 `iter_nodes()`，**所有**消费节点的函数
（asset_stats / topo_root_hash / build_kb_index / cmd_verify / cmd_list / render_topo_html）都走它：

```
节点数 = Σ 组内资产（行）
       + Σ 子图谱节点（每个 1 个 · 库本体/镜像组本身）
       + Σ 子图谱内嵌笔记资产（Obsidian 笔记等叶子）
= 19 + 3 + 1 = 23
```

| 规则 | 依据 |
|:---|:---|
| 子图谱节点 = 1 个节点 | 库本体是**可验证实体**（有 DNA/状态/link/行数），不是空壳容器，本身就该被 verify |
| 子图谱内嵌笔记逐条计 | 笔记是叶子资产，有独立 DNA/状态/`file://` 链接，能逐条 verify |
| 不把子图谱「展开到行」 | 国家库 38 行是它**内部数据**，属于该库的内容层，不摊进总台节点数。摊了 = 23 变 60+ = 膨胀 |
| 不把 page 枢纽当子图谱 | 枢纽就是总台行本身，双计 = 造假实体 |

### 4.3 为什么 23 而不是别的数

| 方案 | 节点数 | 问题 | 裁决 |
|:---|:---:|:---|:---:|
| 平面 19 | 19 | 子图谱层消失，两库+镜像无存在感 | 已被本任务淘汰 |
| 全量入图（含 404 库 + 917 笔记） | 数百 | 不可验证实体 + 数量爆炸，verify 名存实亡 | ❌ |
| **本方案（决策一+二+三）** | **23** | 每节点可验证、结构真实、层级清晰 | ✅ **封板** |

23 的意义：**每一个节点都能被 verify 逐项验证**（DNA+链接+状态），没有任何一个节点是凑数的。

### 4.4 后续任何节点变动都自动走同一规则

- 加库：须满足 §2.2 判定公式，走 `lh topo subgraph`
- 加镜像：须满足 §3.3 判定标准，走 `lh topo obsidian sync`
- verify/stats/root_hash/HTML 无需单独维护 —— iter_nodes 是唯一入口，一处改全局一致
