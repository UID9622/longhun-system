### 2.2 架构设计（How to Build）
架构选型：单体优先，预留微服务扩展
```javascript
第一阶段（MVP）: 单体架构
┌─────────────────────────────────────────┐
│           应用层（Node.js）              │
│  ┌────────┐  ┌────────┐  ┌────────┐    │
│  │ MCP核心 │→│  NLP   │→│ 缓存层 │    │
│  └────────┘  └────────┘  └────────┘    │
├─────────────────────────────────────────┤
│          数据层                          │
│  ┌────────┐          ┌────────┐        │
│  │MongoDB │          │ Redis  │        │
│  └────────┘          └────────┘        │
└─────────────────────────────────────────┘

第二阶段（扩展）: 微服务架构（按需拆分）
┌──────────┐  ┌──────────┐  ┌──────────┐
│ API网关  │→│ MCP服务  │→│ NLP服务  │
└──────────┘  └──────────┘  └──────────┘
       ↓             ↓             ↓
  ┌────────┐   ┌────────┐   ┌────────┐
  │消息队列 │   │MongoDB │   │ Redis  │
  └────────┘   └────────┘   └────────┘
```
为什么先选单体？
- ✅ 快速验证：2-3周可上线MVP
- ✅ 降低复杂度：无需配置中间件、服务发现
- ✅ 易于调试：单进程，日志集中
- ✅ 成本低：一台服务器即可
何时拆分微服务？
- 📈 并发量：单机QPS超过5000
- 👥 团队规模：开发人员超过10人
- 🔄 业务复杂度：模块间依赖复杂，频繁冲突

```javascript

L2 用户数据（邮箱、贡献） → 脱敏存储，定期备份
```

### 3.3 代码管理规范
Git分支策略（GitHub Flow）：
```javascript
main（生产分支）
  ↑
  └─ feature/add-nlp-module ← 开发新功能
  └─ fix/cache-bug          ← 修复Bug
  └─ docs/update-readme     ← 更新文档
  └─ refactor/http-client   ← 重构代码
```
分支命名规范：
- feature/功能名 - 新功能
- fix/bug描述 - Bug修复
- docs/文档名 - 文档更新
- refactor/模块名 - 重构
- test/测试描述 - 测试补充
Commit Message规范（Conventional Commits）：
```bash
feat: 添加中文分词功能
```
