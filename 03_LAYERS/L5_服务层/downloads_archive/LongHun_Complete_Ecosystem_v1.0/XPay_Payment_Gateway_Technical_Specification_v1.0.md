## 支持的币种

### 第一类: 官方认可（完全支持）

```
✅ 数字人民币 (e-CNY)
   标准: 官方数字货币，天然满足所有条件
   手续费: 0% (网关成本价)
   结算: T+0 (实时)
   
✅ 其他达标法币 (Future)
   入选条件:
     1. 来自某个国家的官方法币（非民间币）
     2. 完全可追溯（银行系统提供证明）
     3. 点对点支持（不强制走第三方）
     4. 不可篡改（时间戳完整）
   
   示例（待认证）:
     • 美元 USD (如果美联储推出清晰的CBDC)
     • 欧元 EUR (如果欧央行达成共识)
     • 日元 JPY (如果日本银行提供清晰接口)
```

### 第二类: 观察中（有条件支持）

```
🟡 传统银行国际转账
   条件: SWIFT 或类似的点对点协议
   问题: 通常不符合"不走第三方"的原则
   支持: 仅作为备选通道，不推荐
   
🟡 其他国家的实验性CBDC
   条件: 需要逐案例审查
   流程: 
     1. 国家向XPay提交申请和技术文档
     2. XPay审查是否达到标准
     3. 审查通过后上线测试
     4. 测试通过后正式支持
```

### 第三类: 不支持（明确拒绝）

```
❌ 比特币、以太坊等投机币
   理由: 
     • 价格波动大（不稳定）
     • 第三方托管（中心化风险）
     • 投机属性强（用户易亏）
     • 与"清晰支付"的目标不符
   
❌ 稳定币 (USDT, USDC等)
   理由:
     • 本质是第三方发行
     • 实际储备难以验证
     • 违背"点对点"原则
   
❌ 暗币、隐私币 (Monero, Zcash等)
   理由:
     • 无法追溯
     • 违反合规要求
     • 无法证明资金来源
```

## 交易流程

### 标准交易流程（7步）

```
【步骤1】发起交易
  用户 → XPay Gateway
  输入: 
    • 金额 (amount)
    • 币种 (currency)
    • 收款地址 (recipient)
    • 备注 (memo, optional)
  输出: transaction_id
  
【步骤2】交易验证
  验证项:
    ✓ 币种是否被支持
    ✓ 金额是否合法（>0, <=max）
    ✓ 地址格式是否正确
    ✓ 发起人身份是否已认证
    ✓ 账户是否有足够余额
  结果: 通过 → 步骤3 / 失败 → 拒绝
  
【步骤3】风险评估
  评估项:
    • 是否存在可疑交易模式
    • 账户历史中是否有异常
    • 收款方是否在黑名单中
    • 金额是否超过单笔限额
  结果: 低风险 → 步骤4 / 高风险 → 人工审核
  
【步骤4】费率计算
  计算:
    base_fee = 0% (for e-CNY) 或 <0.5% (for others)
    network_fee = 根据网络拥堵程度
    total_fee = base_fee + network_fee
  
【步骤5】清结算处理
  动作:
    • 冻结发起人账户（金额+手续费）
    • 连接到相应的银行/清算通道
    • 发送指令到银行系统
    • 等待银行确认
  确认: 银行返回结算凭证 (settlement_proof)
  
【步骤6】龍魂系统记录
  记录:
    • DNA时间戳 (不可篡改)
    • 完整的交易信息 (压缩)
    • BehavCrypto签证
    • 版本号 (递增，永不重复)
  存储: 本地 + 分布式备份
  
【步骤7】交易完成
  回复给用户:
    • 交易ID (transaction_id)
    • 状态 (completed)
    • DNA签证 (dna_signature)
    • 永恒记录ID (eternal_record_id)
    • 时间戳 (immutable_timestamp)
  可选: 将记录存到用户的本地备份
```

### 异常处理流程

```
【场景1】交易被拒绝
  → 用户收到错误消息和原因代码
  → 无金额冻结
  → DNA日志记录"拒绝"事件
  
【场景2】高风险交易被标记
  → 发送给风险审核团队
  → 用户账户暂时锁定（可解锁）
  → DNA日志记录"风险标记"事件
  
【场景3】银行系统返回失败
  → 自动重试（最多3次）
  → 如果仍失败，退款并通知用户
  → DNA日志记录"结算失败"事件
  
【场景4】用户主动取消交易
  → 如果未开始清结算，直接取消
  → 如果已开始，等待银行返回后退款
  → DNA日志记录"用户取消"事件
```

## 安全机制

### 1️⃣ 身份认证（Identity）

```
多层认证:
  • 账户密码 (基础)
  • 手机验证码 (短信OTP)
  • 生物识别 (指纹/人脸)
  • 硬件密钥 (可选，最安全)

存储:
  • 密码: bcrypt 哈希 (不可逆)
  • OTP: 一次性使用，自动过期
  • 生物: 本地加密存储 (不上云)
  • 密钥: 用户离线保管
```

### 2️⃣ 数据加密（Encryption）

```
传输层:
  • TLS 1.3 (所有网络通信)
  • 强制HTTPS (不允许HTTP)
  
存储层:
  • AES-256 加密 (敏感数据)
  • 密钥分离 (不在同一地方)
  
本地:
  • 用户机器: 本地加密存储
  • 不依赖云端密钥管理
```

### 3️⃣ 交易签名（Signature）

```
每笔交易:
  • 发起者数字签名 (RSA-4096 或 EdDSA)
  • 交易序列号 (防重放)
  • 时间戳 (防时间混淆)
  
验证:
  • 服务器验证签名
  • 如果验证失败，交易拒绝
```

### 4️⃣ 审计日志（Audit Trail）

```
特点:
  ✓ 追加日志（append-only）
  ✓ 不可删除（immutable）
  ✓ 完整链式（chained）
  ✓ 用户可查阅（transparent）
  
包含:
  • 登录记录
  • 每笔交易
  • 异常事件
  • 管理员操作
```

### 5️⃣ 反欺诈（Fraud Prevention）

```
实时检测:
  • 异常交易金额
  • 异常交易地域
  • 连续快速交易
  • 已知欺诈地址
  
机制:
  • 交易限额（每日/每月）
  • 异常锁定（提示用户）
  • 人工审核（高风险）
  • 黑名单管理（共享）
```

## 龍魂系统集成

### 1️⃣ DNA时间戳集成

```
每笔交易都包含:
  • created_at: ISO 8601 时间戳
  • sequence_number: 递增的序列号
  • previous_hash: 前一笔交易的哈希
  • data_hash: 这笔交易的内容哈希
  • timestamp_hash: 时间戳自身的哈希
  
特性:
  ✓ 形成不可篡改的链
  ✓ 任何修改都能被检测
  ✓ 无法删除（删除会破坏链）
```

### 2️⃣ DNA压缩集成

```
交易存储:
  原始: JSON 格式（可读）
  压缩: zlib 压缩 + Base64 编码
  
效果:
  • 节省 30-50% 存储空间
  • 保持完整可还原性
  • 提高传输速度
  
格式: LH_DNA.1.0.{checksum}.{encoded_data}
```

### 3️⃣ BehavCrypto签证集成

```
每笔交易的签证:
  #龍芯⚡️{timestamp}-{tx_id}-DR{digital_root}-{hash_short}
  
用途:
  • 唯一标识这笔交易
  • 证明交易来源
  • 防止冒充
  • 永久追踪
```

### 4️⃣ 版本控制集成

```
交易记录:
  • 版本号: 递增 (1, 2, 3, ...)
  • 变更描述: 详细说明这个版本的变化
  • 作者: 谁执行的操作
  • 变更时间: 完整的时间戳
  
特性:
  ✓ 只增不删 (append-only)
  ✓ 完整的修改历史
  ✓ 可审计每一步
```

### 5️⃣ 永恒记录集成

```
交易的永恒化:
  1. 交易完成后立刻进入永恒库
  2. 分布式备份（IPFS/Arweave）
  3. 用户本地备份
  4. 合规归档
  
承诺:
  ✓ 任何中心化系统宕机都无法删除
  ✓ 即使XPay服务关闭，记录永久存在
  ✓ 用户始终拥有自己的数据
```
