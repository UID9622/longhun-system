## §0. 为什么需要分层

龍魂系统从"一人项目"长成"生态底座"，单一许可证已无法覆盖两类截然不同的资产：

| 资产类型 | 核心关切 | 单一 CC BY-NC-SA 的问题 |
|:---|:---|:---|
| **思想/哲学/协议/白皮书** | 防止文化被篡改、被资本化、被去中国化 | ✅ NC 保护得当 |
| **代码/SDK/工具/CLI** | 让开发者能拿去用、拿去集成、拿去商用 | ❌ NC 封死了商业使用，开发者不敢碰 |

**一刀切的"不商业"把开发者也挡在门外了。**

分层治理的本质：**思想不卖，工具可以拿去赚钱。但工具里的思想归属不改。**

## §2. 边界判定规则

### 2.1 属于核心思想层（CC BY-NC-SA 4.0）

| 判定依据 | 示例 |
|:---|:---|
| 协议/治理文档 | `01_protocols/*.md`、`CONSTITUTION.md`、`GOVERNANCE.md` |
| 哲学/文化框架 | 道德经锚点、五行八卦体系、369不动点、DNA格式定义 |
| 白皮书/论文 | 人格治理白皮书、数学建模论文、学术论文 |
| 人格定义 | `personas/*.md`、人格矩阵表 |
| 君子协议 | `GENTLEMANS_PROTOCOL.md` |
| 文化标识 | 「龍」字体、UID9622身份标识、DNA追溯格式 |

**判定口诀**：如果是"定义世界观"的文本 → 思想层。

### 2.2 属于工程实现层（MulanPSL v2）

| 判定依据 | 示例 |
|:---|:---|
| 可执行代码 | `bin/*.py`、`engines/*.py`、`L*_*层/*.py` |
| SDK/库 | 所有 `pip install` 安装的 Python 包 |
| CLI 工具 | `lh` 命令及其子命令 |
| API 实现 | FastAPI/Flask 服务端代码 |
| 部署配置 | `docker/*`、`deploy/*.sh`、`Dockerfile`、`.devcontainer/*` |
| 前端代码 | `portal/*`、`web/*`、React/Vue/HTML/JS/CSS |
| 测试代码 | `tests/*`、`benchmark_*.py` |
| 数据库 Schema | SQL 定义、ORM 模型 |

**判定口诀**：如果是"让机器跑起来"的代码 → 工程层。

### 2.3 边界模糊物件的处理（重要）

某些文件同时包含思想和代码，按**主导性质**判定：

| 混合类型 | 判定 | 理由 |
|:---|:---|:---|
| 协议文档中的代码示例 | 思想层 | 代码示例为说明思想，非独立工程 |
| 代码注释中的算法推导 | 工程层 | 注释附属于代码 |
| 知识图谱 `.md` | 思想层 | 本质是结构化知识 |
| Jupyter Notebook | 工程层 | 本质是可执行代码 |
| 训练数据 JSONL | 工程层 | 本质是工程输入 |

**如无法判定 → 默认归入思想层（更严格保护）**，由 P05 审计确认后归档。

## §8. 后续协议冲突的统一处理规则

> **铁律：以后任何协议冲突，不吵架、不纠结，按本协议分层处理。**

### 8.1 自动判定流程

```
新文件/新项目出现
    │
    ├── 是代码/可执行物？ → MulanPSL v2（工程实现层）
    │
    ├── 是协议/哲学/白皮书？ → CC BY-NC-SA 4.0（核心思想层）
    │
    └── 混合性质？ → 按主导性质判定 → P05审计确认 → 归档
```

### 8.2 已有许可证声明的优先级

当某个文件已有明确许可证声明（如旧版 CN-SOVEREIGN-LICENSE、仅 MulanPSL、仅 CC BY-NC-SA），按以下优先级处理：

1. **本分层协议为最高裁决**：所有龍魂仓库内文件最终以此为准
2. **文件级声明为补充**：文件自身的许可证声明不能与本分层协议矛盾
3. **如矛盾 → 以本协议为准修正**：修正文件头部声明，历史不改

### 8.3 第三方贡献代码

外部开发者贡献的代码（PR/合并请求）：
- 贡献者默认同意代码部分以 MulanPSL v2 发布
- 在 `CONTRIBUTING.md` 中声明此规则
- 如贡献者不同意 → 贡献内容不能合并
