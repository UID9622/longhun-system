## 第一条: 核心问题

系统会越来越多（L0-L9 九层 · 192+引擎 · 45工具）。
靠一个人手改文档、手发通知、手升版本 = 不可能，结构就白搭。

**结论**: 信息从中枢一句话广播，经群结构直达每一个点（引擎），每个点收到后**自动升级**自己。文档三段（使用说明/版本/接口）由引擎**实时生成**，不靠人手。

---

## 第二条: 群结构定义

### 2.1 拓扑

```
          中枢(MESH-HUB / UID9622指令)
                 │ 广播(broadcast)
   ┌─────────────┼─────────────┐
   ▼             ▼             ▼
 点A(引擎)     点B(引擎)     点C(引擎)   ← 每个点同时是接收者+中继
   │ 中继          │ 中继          │ 中继
   ▼             ▼             ▼
 点D           点E           点F
```

- **点(node)**: 任意一个可执行引擎/脚本/服务，含唯一 DNA、版本、接口清单、文档路径。
- **群(group)**: 按层（L1内核/L2技能/L3路由…）或职能聚合的点的集合。
- **中枢(hub)**: UID9622 指令入口，发起广播，不逐点手动操作。
- **直达**: 广播一发出，日志落盘即视为「已到达每个点」；每个点独立执行自己的升级例程。

### 2.2 一条广播的生命周期

```
中枢 broadcast "<指令>" 
   → 写入 L7_数据层/mesh/broadcast_log.jsonl (带时间戳+DNA)
   → 遍历所有点 node
   → 每点调用自身 node_auto_upgrade():
        1. 重新抽取版本(源码DNA/VERSION)
        2. 重新抽取接口(CLI --help / FastAPI routes)
        3. 重新生成文档三段(使用说明/版本/接口)
        4. 源码哈希变化 → 版本号 minor+1 并标记「已升级」
        5. 写入该点 upgrade_log
   → 返回「直达 N 点 · 自动升级 M 点」
```

## 第三条: 技术文档三段铁律（P0级）

**每一个技术文档，必须实时包含以下三段，缺一视为未完成（诚信标记 L5 违规）：**

| 段 | 标记 | 内容 | 来源 |
|----|------|------|------|
| 使用说明 | `## 使用说明` | 命令/调用示例，可直接复制运行 | 引擎扫描 `python3 <脚本> --help` |
| 版本 | `## 版本` | 当前版本号 + 最后同步时间(干支时间戳) | 源码 `VERSION`/`DNA`/文件哈希 |
| 接口 | `## 接口` | CLI参数 或 API路由(方法+路径+入参) | argparse / FastAPI decorator 抽取 |

- **实时**: 由 `bin/lh_mesh_sync.py` 自动抽取生成，禁止手写后长期不更新。
- **版本**: 源码改动 → 重算哈希 → minor 自增，文档版本同步刷新。
- **接口**: 引擎暴露什么，文档就写什么，一一对应。

---

## 第四条: 自动升级规则

| 触发 | 行为 |
|------|------|
| 中枢 `broadcast` | 每点执行 node_auto_upgrade，重抽版本/接口/文档 |
| 源码哈希变化 | 点版本 minor+1，标记「已升级」，文档刷新 |
| 新增引擎 | `scan` 发现后自动入群，生成三段文档 |
| 定时守护 | `daemon` 周期扫描，变化即同步，无需人工 |

**不靠一人维护**: 加引擎、改接口、升版本，全部由群结构自动完成；UID9622 只发一句话。
