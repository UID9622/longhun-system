## 一、協議概述

### 1.1 目標與哲學

**核心哲學：**「先讀懂、再決定怎麼接。」

本協議定義龍魂體系處理一切外部輸入時的標準化流程。任何來自用戶、傳感器、API或文件的輸入，在進入認知處理鏈之前，必須經過本協議定義的過濾與預處理流程。

**存在理由：**
- 未經過濾的輸入是認知混亂的第一根源
- 垃圾進、垃圾出（GIGO, Garbage In Garbage Out）—— 輸入質量決定輸出質量
- 本協議是認知守門人，不是可選插件

### 4.1 階段一：感知層 — 語義錨點提取與結構化封裝

**映射：** 感知層（輸入篩查）→ 監督器第一層

**目標：** 將任何形式的輸入轉化為結構化、可理解的內部表示。

**4.1.1 關鍵詞掃描**
- 自動識別輸入中的核心實體、動作、約束條件
- 標記時間表達、數值表達、否定表達、條件表達
- 輸出：`語義錨點列表（Semantic Anchor List）`

**4.1.2 結構化封裝（LongHunInput 格式）**

所有輸入必須封裝為以下標準結構：

```json
{
  "cnsh_header": "#龍[INPUT]⚡️[ISO8601]-INPUT-FILTER-v3.0",
  "raw_input": "原始輸入內容",
  "semantic_anchors": [
    {"type": "entity", "value": "...", "position": 0},
    {"type": "action", "value": "...", "position": 1},
    {"type": "constraint", "value": "...", "position": 2}
  ],
  "input_type": "user_query|api_call|file_import|sensor_data",
  "completeness_score": 0,
  "clarity_score": 0,
  "risk_flags": [],
  "audit_trail": []
}
```

**4.1.3 非結構化數據清洗**
- 去除輸入中的無意義噪聲（多餘空格、亂碼、重複標點）
- 保留原始副本，清洗結果存入 `cleaned_input` 字段
- 記錄清洗操作到 `audit_trail`

**感知層評分標準：**

| 評分項 | 權重 | 評分標準 |
|--------|------|----------|
| 錨點識別率 | 30% | 核心實體是否全部捕獲 |
| 結構化完整度 | 30% | LongHunInput 必填字段是否完整 |
| 噪聲隔離度 | 20% | 無關信息是否有效清除 |
| 語義清晰度 | 20% | 輸入意圖是否可明確解讀 |

---

### 4.2 階段二：認知層 — 多維衝突檢測與缺失識別

**映射：** 認知層（邏輯驗證）→ 監督器第二層

**目標：** 在結構化輸入中發現邏輯問題、數值衝突和信息缺口。

**4.2.1 數值一致性校驗**
- 掃描所有數值表達，檢查單位一致性
- 檢查數值是否在合理邊界內
- 檢查多個數值之間的數學關係是否自洽
- **觸發條件：** 發現數值衝突 → 生成紅色標記，阻斷或要求澄清

**4.2.2 邊界越界檢測**
- 檢查輸入中的數值是否超出業務約束範圍
- 檢查輸入長度、複雜度是否在處理能力範圍內
- 檢查輸入頻率是否觸發限流閾值
- **觸發條件：** 發現越界 → 生成紅色標記，立即阻斷

**4.2.3 衝突熔斷（Conflict Circuit Breaker）**
- 檢測同一輸入中的自相矛盾陳述
- 檢測輸入與系統已知事實的衝突
- 檢測多個輸入之間的不一致
- **熔斷機制：** 衝突嚴重度達到閾值 → 立即中斷處理，返回澄清請求

**4.2.4 完備性自檢**
- 對照當前任務類型的標準參數列表，檢查必需參數是否全部提供
- 標記缺失參數，評估缺失對處理結果的影響程度

**4.2.5 假設前置聲明**
- 當輸入存在隱含假設時，系統必須明確聲明這些假設
- 格式：「基於您的輸入，我做出以下假設：[假設內容]。請確認或修正。」

**認知層評分標準：**

| 評分項 | 權重 | 評分標準 |
|--------|------|----------|
| 數值一致性 | 25% | 所有數值無衝突 |
| 邊界合規性 | 25% | 無越界檢測項 |
| 衝突熔斷狀態 | 25% | 無熔斷觸發 |
| 完備性分數 | 25% | 必需參數覆蓋率 |

---

### 4.3 階段三：決策層 — 交互確認與證據鏈生成

**映射：** 決策層（行為審核）→ 監督器第三層

**目標：** 確保處理決策有充分依據，所有行為可追溯。

**4.3.1 主動核實（Proactive Verification）**
- 當認知層發現黃色或紅色標記時，系統主動向用戶發出澄清請求
- 澄清請求必須具體、可執行，不籠統
- 澄清請求格式：「發現[具體問題]，請確認：[選項A/選項B/提供更多細節]」

**4.3.2 DNA證據鏈（DNA Evidence Chain）**

每個通過過濾的輸入必須附帶完整的證據鏈：

```
證據鏈格式：
┌─────────────────────────────────────────┐
│  輸入ID: [唯一標識符]                    │
│  時間戳: [ISO8601]                       │
│  感知層評分: [X/100] + [評分依據摘要]    │
│  認知層評分: [X/100] + [評分依據摘要]    │
│  決策層評分: [X/100] + [決策依據摘要]    │
│  綜合評分: [X/100] 🧬                    │
│  審計色: 🔴 / 🟡 / 🟢                   │
│  放行決策: [通過 / 阻斷 / 需澄清]        │
│  操作人: [AI實例標識]                    │
│  簽名: [SHA256摘要]                      │
└─────────────────────────────────────────┘
```

**4.3.3 置信度計算**

最終置信度 = 感知層評分 × 0.3 + 認知層評分 × 0.4 + 決策層評分 × 0.3

| 綜合分數區間 | 決策 | 行動 |
|-------------|------|------|
| 0 - 29 | 阻斷 | 拒絕處理，記錄日誌，通知用戶 |
| 30 - 59 | 警告 | 標記風險，主動澄清，降級處理 |
| 60 - 79 | 通過 | 放行進入下游，附帶審計標記 |
| 80 - 100 | 優秀 | 完全放行，推薦加速處理 |

## 五、系統內部自檢清單（飛行前自檢）

> 原名「Pre-flight Check」，現統一使用中文術語「飛行前自檢」。

在每個輸入進入處理鏈之前，系統必須完成以下五項自檢：

```
╔══════════════════════════════════════════════════════════════╗
║                 【飛行前自檢清單】                            ║
║                  v3.0 — 五項必檢                             ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║  □ 1. 識別完整性（Identification Completeness）              ║
║        └─ 輸入中的核心實體是否全部識別？                     ║
║        └─ 是否有無法歸類的語義碎片？                         ║
║        └─ 未識別內容是否標記待澄清？                         ║
║                                                              ║
║  □ 2. 邏輯自洽性（Logical Consistency）                      ║
║        └─ 輸入內部是否存在自相矛盾？                         ║
║        └─ 數值關係是否數學自洽？                             ║
║        └─ 條件陳述是否閉合？                                 ║
║                                                              ║
║  □ 3. 噪聲隔離度（Noise Isolation）                          ║
║        └─ 無關信息是否有效清除？                             ║
║        └─ 清洗過程是否保留原始副本？                         ║
║        └─ 噪聲比例是否在可接受範圍？                         ║
║                                                              ║
║  □ 4. 獨立可解性（Independent Solvability）                  ║
║        └─ 當前輸入是否包含足夠信息獨立處理？                 ║
║        └─ 缺失信息是否已識別並標記？                         ║
║        └─ 是否存在未聲明的隱含依賴？                         ║
║                                                              ║
║  □ 5. 確認機制觸發（Confirmation Trigger）                   ║
║        └─ 是否存在紅色標記（阻斷級問題）？                   ║
║        └─ 是否存在黃色標記（警告級問題）？                   ║
║        └─ 是否已生成針對性澄清請求？                         ║
║        └─ 用戶確認是否已收到並記錄？                         ║
║                                                              ║
╚══════════════════════════════════════════════════════════════╝
```

**自檢規則：**
- 五項全部通過 → 輸入進入下游處理鏈
- 任意一項未通過 → 輸入暫留本層，觸發對應修復流程
- 第5項中的紅色標記 → 強制阻斷，不可繞過
