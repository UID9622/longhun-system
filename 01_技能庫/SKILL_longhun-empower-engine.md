## 二、核心理念

### 2.1 核心哲学

| 序号 | 理念 | 阐释 |
|------|------|------|
| 1 | **别人的算法让你上瘾，我们的算法让你离开** | 赋能引擎的目标是帮用户解决问题后自然退出，不是制造依赖 |
| 2 | **不是检测违禁词，是听出真实需求** | 不同于传统敏感词过滤，引擎理解语义背后的真实诉求 |
| 3 | **不是打标签，是找到该去的水流方向** | 关键词匹配不是贴标签，是路由到最合适的处理人格 |
| 4 | **上善若水** | 赋能不是给人贴标签，是让水流到该去的地方——柔软、顺势而为、润泽万物 |

### 2.2 设计原则

- **人优先于词**：同样的词在不同语境下含义不同，引擎看上下文不看孤立词
- **情绪优先于方案**：用户有情绪时，先接情绪再给方案，顺序不可颠倒
- **护底优先于中立**：维权类需求自动站普通人一边，不做"和稀泥"式判断
- **本地优先于云端**：所有识别在本地完成，用户数据不上传第三方
- **透明优先于黑盒**：识别逻辑和评分标准完全开源，任何人可审计

### 2.3 反流量垄断立场

引擎内置反流量垄断评分系统，当检测到以下特征时自动告警：

- **收割词**："限时"、"必抢"、"错过等一年"、"全网最低"等制造焦虑的营销话术
- **成瘾设计识别**：无限滚动、随机奖励、社交比较的语义模式
- **赋能词加权**："自立"、"开源"、"本地可控"、"数据主权"等正向表达加分

> ⚠️ 反垄断评分是**参考**，不是绝对判断。最终决策权在用户手中。

| 场景 | 处理方式 |
|------|----------|
| 情绪 + 任何其他 | 情绪优先，P02宝宝先接，稳定后再路由其他 |

### 5.3 异常处理

| 异常场景 | 处理策略 |
|----------|----------|
| 无法识别任何类别 | 返回 `{"primary_persona": "P01诸葛亮", "reason": "需求不明确，建议进一步沟通"}` |
| 文本超5000字 | 截断前5000字处理，返回中标注 `truncated: true` |
| API异常 | 返回HTTP 500 + 错误详情，记录审计日志 |
| 全类别低置信度(<0.3) | 降级为P01诸葛亮通用咨询模式 |

## 六、输入规范

### 6.1 输入格式

| 属性 | 要求 |
|------|------|
| **类型** | 文本字符串（UTF-8编码） |
| **最大长度** | 5000字（含标点） |
| **最小长度** | 2字（低于2字返回降级处理） |
| **编码** | UTF-8 |
| **语言** | 中文为主，兼容中英文混合 |

### 6.2 输入示例

```
✅ 有效输入：
   - "最近工作好累，天天加班到半夜，身体快撑不住了"
   - "我想学Python，有没有好的入门资源推荐"
   - "公司拖欠工资三个月了，劳动仲裁流程怎么走"
   - "这个API总是返回500错误，帮我看看代码"
   - "平台限流太严重了，我的账号数据他们是不是在监控"

❌ 无效输入：
   - ""（空字符串）
   - "a"（单字符，低于2字）
   - [超过5000字的长文本]
   - 纯二进制/非文本内容
```

### 6.3 预处理规则

1. **清洗**：去除首尾空白、标准化标点（全角转半角）
2. **分句**：按句号/问号/感叹号分句，便于上下文分析
3. **去噪**：去除URL、@提及、重复字符（如"好~~~~"标准化为"好~"）
4. **保留原文**：预处理后仍保留原始文本用于最终输出引用

## 八、边界与限制

### 8.1 功能边界

| 边界 | 说明 |
|------|------|
| **不是通用AI助手** | 引擎只做"需求识别 + 人格路由"，不直接生成完整回答 |
| **不替代人格功能** | 路由结果只是建议，最终由被调用的人格完成实际输出 |
| **不做情感判断** | 识别"有情绪"但不判断情绪好坏，不做价值评判 |
| **不做法律裁决** | 维权类需求识别后路由到专业人格，引擎本身不给法律建议 |
| **不处理涉密内容** | 涉密、敏感政治内容超出处理范围 |

### 8.2 数据主权声明

- **本地优先**：所有识别逻辑在本地运行，不依赖云端API
- **数据不上传**：用户输入文本仅用于本地识别，不上传任何第三方
- **审计日志本地存储**：日志存储在本地，用户可完全控制
- **可选Notion推送**：Notion推送需用户手动开启并自行配置Token

### 8.3 安全限制

- 🔒 **不在公开仓库提交** `config.json` 或任何密钥文件
- 🔒 **不记录**用户原始输入的完整文本（仅记录摘要和识别结果）
- 🔒 **不反向追踪**用户身份（无用户画像、无行为追踪）

### 8.4 反垄断评分声明

> ⚠️ 反垄断评分是**参考**，不是绝对判断。评分基于关键词匹配和加权算法，可能存在误判。最终决策权始终在用户手中。引擎对评分结果不承担法律责任。

| 复合需求 | "好累，代码还报错" | → P02宝宝(主) + P04鲁班(次) | 情绪优先，稳定后再处理技术 |
| 教育规划 | "想学编程但不知道从何开始" | → P14吕蒙 | 士别三日，制定学习路线图 |

### 9.2 ❌ 坏的实践（RED）

| 场景 | 错误做法 | 问题 |
|------|----------|------|
| 情绪错判 | 把"好累不想干了"识别为"需要分析原因" | 违反"先接住"原则，用户需要被理解不是被分析 |
| 维权和稀泥 | 把"欠薪"识别为"劳资纠纷建议协商" | 违反"站普通人一边"原则，默认站资方 |
| 人格错配 | 把"孩子不听话"路由到P01诸葛亮 | 家庭问题需要P02宝宝或P15乔前辈的温情处理 |
| 忽略上下文 | 把"虽然累但我有办法"识别为纯情绪 | 用户已自我疏导，应尊重其主动性 |
| 技术傲慢 | 把"我不会用"识别为"能力问题" | 应路由到P14吕蒙耐心教学，而非批评 |

### 9.3 质量检查清单

在每次路由决策后，自检以下问题：

- [ ] 用户有情绪吗？有 → 必须P02宝宝先接
- [ ] 涉及维权吗？有 → 必须P05上帝之眼或P12屈原，不中立
- [ ] 是多需求并存吗？是 → 优先级排序正确吗
- [ ] 反垄断评分标注了吗？标注"仅供参考"了吗
- [ ] 路由建议清晰吗？用户能看懂为什么要调用这个人格吗
