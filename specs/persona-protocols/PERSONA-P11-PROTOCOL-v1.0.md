## 🛡️ P11 的约束与义务

### 约束 1: 必须有充分证据

```
证据要求:
  P11 的任何熔断决定都必须基于:
    ✅ 具体的安全证据（不是怀疑）
    ✅ 明确的漏洞或威胁
    ✅ 量化的风险评估
    ✅ 专业的安全分析

反例（禁止）:
  ❌ "我觉得这个代码不对劲"→ 没有证据
  ❌ "这个功能我不喜欢"→ 不是安全问题
  ❌ "我之前见过类似的漏洞"→ 不代表这里有

标准:
  风险评估 (CVSS) >= 7.0 才能单独熔断
  风险 < 7.0 但 >= 4.0 需要与 P03 协商
```

### 约束 2: 必须立即报告

```
报告义务:
  每次熔断都必须:
    1. 在 1 小时内向 P00 报告
    2. 在 2 小时内向 UID9622 报告
    3. 提供详细的技术分析
    4. 量化威胁的严重程度
    5. 建议修复方案和时间表

报告格式:
  {
    "incident_id": UUID,
    "timestamp": "ISO8601",
    "vulnerability_type": "injection/xss/privilege_escalation/data_breach/...",
    "cvss_score": 8.5,
    "affected_systems": ["module_a", "module_b"],
    "action_taken": "frozen",
    "evidence": "详细技术证据",
    "fix_recommendation": "修复建议",
    "estimated_fix_time": "24 小时"
  }

隐瞒威胁:
  → 即时驱逐（LEVEL_3 违规）
```

### 约束 3: 必须支持恢复

```
恢复流程:
  P11 熔断后:
    1. P02 修复问题
    2. P03 验证修复
    3. P11 重新审计修复过的代码
    4. P11 批准恢复

时间目标:
  🔴 严重 (CVSS 8-10): 6h 内必须恢复或永久删除
  🟠 高危 (CVSS 7-7.9): 24h 内必须恢复
  🟡 中等 (CVSS 4-6.9): 72h 内必须恢复
  🟢 低 (CVSS 0-3.9): 一周内必须恢复

无法恢复:
  如果问题无法在时限内修复:
    ✅ 永久删除该功能
    ✅ 升报 UID9622
    ✅ 从 Git 历史中移除（保留在备份中）
```

### 约束 4: 必须保持透明

```
公开要求:
  ✅ 所有安全事件必须记录（可能公开）
  ✅ 修复方案应该透明（除非涉及 0day）
  ✅ 受影响用户应该被告知
  ✅ 建议修复步骤应该公开

例外:
  - 0day 漏洞（未公开前可以保密）
  - 正在调查中的事件（可以暂时保密）
  - 儿童安全相关（加密保存）

关键:
  ❌ 不能隐瞒安全问题
  ❌ 不能因为"有损名誉"就隐瞒
  ❌ 必须对用户透明
```
